# Motion module

`includes/Modules/Motion/`. Settings stored under `lumia_module_motion`. Replaces the former "SK Motion" FluentSnippets snippet (GSAP from a CDN on every page) with entrance and scroll effects for Bricks, adjustable per element. The module does nothing unless Bricks is the active theme.

| File | Role |
|---|---|
| `Effects.php`, `Legacy.php` | Effect catalog and reference values; every former name (`sk-*`, `--sk-hover-underline-*`, the former global and snippet name) lives in `Legacy.php` only |
| `SettingsSanitizer.php`, `settings-template.php` | Admin screen: default tempo and curve, reference values per effect, Lenis, builder preview, compatibility |
| `Controls.php` | "Motion" group on the Style tab of every Bricks element |
| `Marker.php` | `data-lm` on animated elements, inline overrides where the class would win, families used by the page |
| `Assets.php` | Conditional loading, inline styles, loader of the engine after the first paint, configuration JSON |
| `ClassManager.php`, `Command.php` | `lm-*` global classes, `wp lumia motion classes|migrate` |
| `assets/front/js/motion-core.js` | Pure helpers (curves, springs, settings resolution, counter), unit tested with `node --test` |
| `assets/front/js/motion.js`, `motion-scroll.js`, `motion-builder.js` | Engine, Lenis, builder preview |
| `assets/front/js/motion-counter.mjs` → `motion-counter.js` | Counter adapter (source) and its bundle with NumberFlow, one classic script generated by `tools/motion/js/build-counter.mjs`: NumberFlow behind `window.lumiaMotionCounter` |
| `assets/front/js/motion-panel.js` | Builder main window: Replay, "Show markers", inherited placeholders, Motion shortcut in the element rail |

## Using it in Bricks

- **One click:** add a global class from the "Motion" category (`lm-fade`, `lm-slide-up`, `lm-blur`, `lm-blur-up`, `lm-zoom`, `lm-zoom-blur`, `lm-lines`, `lm-words`, `lm-letters`, `lm-counter`, `lm-underline`).
- **Per element:** Style tab > Motion. Every control writes a `--lm-*` CSS variable, so the usual Bricks cascade applies: element > class > module defaults (passed as JSON, not through `:root`). Breakpoint values work like any Bricks control.
- **One effect per element.** With two Motion classes, the first one in the class list wins (`?lmDebug` logs it).
- **Typed class names count too:** a Motion class typed in the element's "CSS classes" field (`_cssClasses`) is marked like a global class (`lm-*` always, `sk-*` while the compatibility setting is on). Before, `Marker` read only the global classes, so a typed name was never pre-hidden and did not load the engine on its own. A field holding dynamic data (`lm-{acf_effect}`) is read as Bricks rendered it: Bricks 2.4.3 renders the dynamic data of each class into the `class` list of the root attributes (`Element::set_root_attributes()`), which `Marker::with_resolved_classes()` takes instead of the raw field, whose name matched no effect.
- **LCP:** entrance effects in the header or the first section play in CSS from the first frame (see "Load animations" below), so they never wait for the scripts. Elsewhere, entrance effects pre-hide the element until the engine is ready; text and counters are never pre-hidden.
- **On load** (`_lmLoad`, `--lm-load`): `auto` (default), `always` (played on load wherever the element is), `never` (always the scroll path). Only the base value counts (element, else its first class with one); breakpoint values are ignored.

### Variables

Engine variables are registered with `@property … inherits: false`, so a child never inherits its section's settings: `--lm-effect`, `--lm-start-edge`, `--lm-start-at`, `--lm-end-edge`, `--lm-end-at`, `--lm-start`, `--lm-end`, `--lm-tempo`, `--lm-duration`, `--lm-delay`, `--lm-stagger`, `--lm-ease`, `--lm-ease-custom`, `--lm-distance`, `--lm-blur`, `--lm-scale`, `--lm-from-opacity`, `--lm-start-value`, `--lm-counter-width`, `--lm-counter-style`, `--lm-load`. `tools/motion/php/EffectsTest.php` checks that the `@property` list of `motion.css` is `Effects::ENGINE_VARIABLES`, in order.

The underline variables are **inheritable** on purpose (a wrapper can restyle every link inside it): `--lm-underline-thickness` (`round(max(1px, 0.06em), 1px)`, so about 1 px on body text and 2 px on a 32 px title; the base rule declares `1px` and the `round()` variant sits in an `@supports (height: round(1px, 1px))` block, because a second `var()` declaration would win everywhere and compute to `auto` without `round()`), `--lm-underline-gap` (0.12em), `--lm-underline-color` (currentColor), `--lm-underline-duration` (0.4s). Never declare them with `@property`.

While the compatibility setting is on, the former `--sk-hover-underline-*` variables are read as a second fallback (`Legacy::underline_css()`, printed after `motion.css`): the drawing rules are repeated with `var(--lm-underline-gap, var(--sk-hover-underline-gap, 0.12em))` and so on. They sit on the drawing rules, not on the former class: a first version assigned `--lm-underline-*` on `.sk-hover-underline`, which no element carries once the migration has renamed the class, and which hid a value inherited from a wrapper. `tools/motion/php/LegacyTest.php` checks that the fallbacks still mirror `motion.css`.

Positions accept ScrollTrigger syntax only (`top 80%`, `center center`, `bottom-=100`); the same rule is tested in PHP and JS from `tools/motion/positions.json`. Durations accept `s` and `ms`. An inline override (`Marker::VALUE_PATTERN`) keeps `+` and `=` for relative positions (`top+=50 80%`) and refuses `;`, `:`, quotes, `<` and braces.

### Tempo and curves

Two independent settings, so an element can change its timing or feel without changing its effect:

- **Tempo:** `very-fast` ×0.5, `fast` ×0.75, `normal` ×1, `slow` ×1.5, `very-slow` ×2 on the duration and the stagger, never on the delay. `custom` uses `--lm-duration` (a typed duration is ignored otherwise; `?lmDebug` says so). The value `exact` of the first trials is still read as `custom`.
- **Curve:** `smooth` (default), `snappy`, `bouncy` (SwiftUI-style springs, bounce 0 / 0.25 / 0.45, computed in `motion-core.js`, no dependency), `linear`, `custom` (`--lm-ease-custom`, a `cubic-bezier()` with x1 and x2 in [0, 1]; invalid → `smooth`). The `lumia` curve of the first trials is still read as `smooth`.
- Opacity and blur always use a no-overshoot variant of the curve; the counter never overshoots whatever the curve; scrub effects (`words`, `letters`) ignore tempo and curve.

### Load animations

Entrance effects (`fade`, `slide-up`, `blur`, `blur-up`, `zoom`, `zoom-blur`) of the first screen are played by `motion.css` from the first frame instead of waiting for the deferred engine: a pre-hidden hero made Chrome pick an invisible LCP, or paint it only after the scripts.

- **Zone** (`LoadAnimation::observe()`, called by `Marker` for every rendered element): every element of the header area, and the first root element (parent `0`) rendered in the content area with all its descendants. A child is in the zone when its parent is (Bricks prints a nestable's root attributes before rendering its children, measured in `container.php` 2.4.2); a component child follows its instance through `parentComponent`.
- **Render area:** Bricks 2.4.2 keeps it in `\Bricks\Frontend::$area` (`header`, `content`, `footer`, `popup`), set by `Frontend::render_data()` for the tree being rendered and put back to the outer area after a nested render (template element, popup, reading time in a loop). `Marker::render_area()` reads it during `bricks/element/render_attributes`. Popups (`popup`) and the footer are never in the zone, a popup not even when Bricks renders it inside a header render (`observe()` tests the area before the outer area). Nothing is in the zone of an AJAX or REST render (`wp_doing_ajax()`, `REST_REQUEST`: a popup or a query page loaded later, a builder call): what it returns is not the first screen. Each `render_data()` also pushes its area on `Frontend::$render_context_stack` (outermost first): a nested render (stack deeper than 1) never claims the first root, and a nested render inside a header render counts as header. Without this, a Template element in the header (mega menu, off-canvas built from a section template) rendered its tree with the area `content` and took the first-root slot: the real first section lost its load animation. `Marker::render_context()` reads both statics; `LoadAnimation::observe()` receives them as arguments.
- **Marking:** an element whose base effect is an entrance, with "On load" `always`, or `auto` and in the zone, gets `data-lm-load="<slug>"` and inline values resolved by `LoadAnimation::attributes()` with the rules of `resolve()` in `motion-core.js` (element > first class with the setting > module values > internal values; tempo scales the duration and the stagger, never the delay; `custom` takes the typed duration and scales nothing; invalid values fall back): `--lm-load-duration`, `--lm-load-move-duration` (duration × `--lm-settle-<curve>` for a spring, the same duration otherwise), `--lm-load-delay` (delay + rank × stagger, the rank counting the earlier load elements with the same effect and values, capped at 7 by `LoadAnimation::MAX_RANK`: from the 8th element of a lot on, every one starts with the 8th, so a query loop of 30 identical cards waits 0.56 s at most instead of 2.4 s), `--lm-load-ease` (`var(--lm-curve-<curve>)`, `linear`, or the custom `cubic-bezier()`), `--lm-load-safe-ease` (`var(--lm-curve-smooth)` for a spring, so opacity and blur never overshoot; the curve itself for `linear` / custom), `--lm-distance`, `--lm-blur`, `--lm-scale`. Never in the builder: the canvas shows the final state and replays through the engine.
- **Text effects and counters of the first screen are shown as written** (`data-lm-settled`). They have no CSS version: before, a hero `lm-lines` title was painted, then the engine (after the first paint) hid its lines and slid them back in, and a hero counter showed its value, then 0, then counted. An element that does not get `data-lm-load`, has a text or counter effect (any breakpoint), "On load" `auto` or `always`, and is in the zone gets `data-lm-settled="text"` / `"counter"` (`Marker::load_attributes()`); `always` does not extend the zone for them. The engine skips it (`skipReason()` returns `settled`): no split, no counter roll, no scrub start state, so a `words` / `letters` scrub keeps every word fully visible. The written text is their final state. To get the animation back on such an element, set **"On load: never"** (« Au chargement : jamais »): the engine animates it as before, after the first paint. Never in the builder: Replay still plays them.
- **Stylesheet:** `[data-lm-load]` and `[data-lm-settled]` (which may hold an entrance on another breakpoint) are left out of the pre-hide rule. One `@keyframes lm-load-<slug>-move` per moving effect (translate or scale), plus `lm-load-fade` and `lm-load-blur`. The fade starts at opacity **0.01, not 0**: Chrome ignores a paint at opacity 0 for the LCP. Keyframes give the start only (the end is the element's own opacity, filter and transform) and the fill is `backwards`: the start state holds during the delay, and once the animation ends it stops applying, so an author's transform or a hover transition is not frozen by a forwards fill. Nothing plays under `prefers-reduced-motion: reduce`.
- **Engine:** `skipReason()` returns `load` for a `[data-lm-load]` element and `settled` for a `[data-lm-settled]` one: no ScrollTrigger, no initial state. Neither counts for the scripts (`Marker::engine_families()`): a page whose effects are all on the first screen loads no GSAP, no engine, no SplitText, no counter module (e2e); its styles stay inline. **Except inside a query loop:** "Load more", infinite scroll, AJAX pagination and query filters add items of the same kind later, rendered by the REST API outside the first screen, and those need the engine; a loop item of the first screen still plays in CSS, but its families count (e2e `edges`). AJAX popups need no such rule: Bricks 2.4.3 renders their content with the page anyway (`Popups::generate_popup_html()` calls `Frontend::render_data()` to drop an empty popup, then leaves out the HTML), so `Marker` sees their elements.
- **Limits:** breakpoint values (and "On load" per breakpoint) do not apply to the load animation; it uses the wide-screen values. An element with a base entrance and a text effect on a smaller breakpoint plays the CSS entrance there too (mobile included), never the text effect; a settled element likewise never plays the entrance of another breakpoint. In a very tall first section, its lower elements animate off screen: set them to "On load: never". A first root that is a Template element is in the zone, but the elements of the template are rendered as a separate tree (their parent is `0` there) and are not; the same goes for page content shown through a Post Content element of a template. With two classes setting the same value, the first class of the element wins (the CSS cascade may pick the other one for the engine path).

## Custom animations: `lumiaMotion.ready()`

For an animation the effects do not cover (a timeline, a pinned section, a marquee), write GSAP by hand and let Motion load it (issue #54). Where to write it, in order of preference:

1. A **Code element** with JavaScript and "Execute code" on (`javascriptCode` + `executeCode: true`), or, by hand in the builder, **Bricks > Page settings > Custom code** (body footer). The call is found on the page and GSAP + ScrollTrigger load there by themselves; SplitText too when the code mentions `SplitText`. **Through MCP (Claude), only the Code element works**: Bricks 2.4.4's `bricks/set-page-settings` refuses any change to the custom scripts whatever the rights (`bricks_code_sensitive_write_forbidden`, `abilities/elements.php`), while a Code element's JavaScript only needs `unfiltered_html` (the Administrator preset of MCP Connect). Without "Execute code", Bricks prints the JavaScript as text in a `<pre>`. Verified on lumia-lp: the element renders a `<script>`, and the page loads the stub and GSAP.
2. **FluentSnippets** (a JS snippet, `wp_footer`, limited by its conditions to the pages it animates), or any other script printed on the page. No page shows that code, but the call itself loads the engine, GSAP and ScrollTrigger on the pages where it runs, and only there (issue #68, see "Loaded on demand" below): no setting to turn on.
3. **Motion > Custom animations > Load GSAP on every page**: only for shared GSAP code that does not go through `lumiaMotion.ready()` (GSAP, ScrollTrigger and SplitText on every public page, after the first paint).
4. From PHP, `add_filter( 'lumia_motion_custom_gsap', '__return_true' )` loads them on the pages it chooses; a falsy value turns every source off on that page, the setting and the on-demand load included.

```html
<script>
lumiaMotion.ready(function (m) {
  // m.gsap, m.ScrollTrigger, m.SplitText (null unless loaded), m.lenis (null without smooth scroll),
  // m.reducedMotion (true when the visitor asked for less motion).
  if (m.reducedMotion) {
    return;
  }
  m.gsap.to(".hero__shape", {
    yPercent: -30,
    ease: "none",
    scrollTrigger: { trigger: ".hero", start: "top top", end: "bottom top", scrub: true },
  });
});
</script>
```

- **The stub.** Page scripts run while the HTML is parsed, long before the engine (injected after the first paint). `Assets::ready_stub_js()`, printed with the head script on every public page and in the canvas (about 170 bytes), defines `window.lumiaMotion.ready()`, queues the callbacks in `lumiaMotion._queue` and calls `lumiaMotion._load()` when the loader left one. The engine's "loaded twice" guard now tests `lumiaMotion.scan`, not the object, so the stub does not stop it; the engine takes the queue over and replaces the object.
- **Loaded on demand** (issue #68). On a public page that does not load the engine (no effect it plays, no call found on the server, setting off), `Assets::print_loader()` registers the engine anyway (`enqueue_engine( false, true )`, then dequeued: WordPress prints no tag) and passes its ordered scripts to the loader as a second list; `window.lumiaMotionConfig` is printed with the loader's data on those pages too (a few hundred bytes). When the loader runs (after the first paint), a non-empty stub queue means a script already called `ready()` (a snippet or a footer script runs while the HTML is parsed): the engine is injected with the other scripts, its libraries before them and `motion.js` after them, the order WordPress gives when it enqueues both (so `motion-scroll.js` sees GSAP and Lenis drives ScrollTrigger). Otherwise the loader leaves `lumiaMotion._load()`, which the stub calls at the first later `ready()`: the engine is injected then, once (Lenis, started earlier without GSAP, keeps its own clock in that case). SplitText is kept only when the source of a queued callback mentions it (`String(fn)`), as the server does for the code it reads; a callback queued later that needs SplitText must say so in an earlier one, or the page must use the setting. Same URLs, same timing, same `lm-ready` on a failed script as the server-side path; nothing on demand in the canvas (the engine is always there) nor when the server already loads the engine (no double load). The filter is asked a second time with `true` and no `$found` when nothing asked for GSAP: a filter that keeps the value allows the on-demand load, `__return_false` keeps it off.
- **When the callbacks run**: after the engine's `start()` (fonts waited for, first build done, `lm-ready` set), so ScrollTrigger measures the final layout; a call made after that runs at once. Each callback is wrapped: an error is logged to the console and the others still run. They do not run in the builder canvas (nothing follows the scroll there: the element shows as written), nor when the engine itself cannot start (GSAP missing, the former snippet still active).
- **Detection** (`CustomGsap`): `Marker` hands the settings of every rendered element to `CustomGsap::observe_element()` (keys `javascriptCode` and `code` of a Code element), and `Assets::custom_gsap()` reads the custom scripts of the page settings of the queried content when it is a post (a page, the posts page, a shop page: `_bricks_page_settings`, keys `customScriptsHeader`, `customScriptsBodyHeader`, `customScriptsBodyFooter`), then the setting, then the filter. **Not read**: the custom scripts of a template (header, footer, or the single template a post is rendered through), and a Code element set to render without its wrapper, if Bricks then skips its root attributes (`bricks/element/render_attributes` is where Marker sees elements). Those calls still load the engine on demand, after the first paint like any other.
- **Load order with smooth scroll** (independent review): the engine used to be queued before `motion-scroll.js`, so on a page whose fonts were already loaded the callbacks ran in the microtask after `motion.js`, before Lenis existed: `m.lenis` was null and ScrollTrigger not yet driven by it. `enqueue_scroll()` now runs before `enqueue_engine()`; `motion-scroll.js` depends on GSAP and ScrollTrigger itself, so it still shares the ticker.
- **Script optimisers**: a "delay JS until interaction" rule must leave the head script (it holds the stub) alone, or a page script calling `lumiaMotion.ready()` before it throws. A stub run after the engine does nothing (`if(m.ready)return`). The engine then loads like for an effect (`enqueue_engine()`, same loader, same `lm-ready` safety), with no item of its own when the page has no effect.
- **Verified** in Chromium with the bundled GSAP: a call before the engine, a call after it, reduced motion (`reducedMotion: true`), the canvas (no call), and smooth scroll on with the scripts in the loader's order (`m.lenis` set, `lenis.on('scroll', ScrollTrigger.update)` wired).

## Decisions and pitfalls

- **Components, global elements, the element holding a query loop:** Bricks writes their settings under `.brxe-{id}` (0,1,0), which loses to the class (0,2,0). `Marker` copies the element's own `_lm*` values into an inline `style`, which wins, at the cost of the element's breakpoint values in these cases. Loop **children** do not need it (`.brxe-loop .brxe-{id}.brxe-{type}`, 0,3,0, measured) and must not get it: it would erase their breakpoint values. Also losing to the class, not handled: nested slider slides (`[data-id].splide__slide`, tie) and a few WooCommerce form elements. The loop test is `Query::is_any_looping()`, as in Bricks' own selector code: `Query::is_looping()` is forced true by the `bricks/query/force_is_looping` filter (AJAX popups) while Bricks still writes the ID selector.
- **Number controls with a fixed unit** are stored bare (`"40"`) and Bricks adds the unit only in its CSS; `Marker::inline_style()` appends it the same way.
- **The `required` conditions of the panel cannot see an effect set by a class**, so the effect settings are always shown. The underline section is the exception (three controls of no use to any other effect): it shows only when the element itself sets the underline effect, so an underline coming from a class is adjusted on the class.
- **Controls are added at `init` priority 100**, after Bricks registers its elements, for every element including add-ons. The builder script is declared only in builder requests: declared on the public site, Bricks prints a `data-script-id` (random inside loops) on every element.
- **`cssLoading = file`:** after changing classes from code, run `wp bricks regenerate_assets` (the migration does it).
- **Counter script:** `motion-counter.js`, one classic script: the adapter (`motion-counter.mjs`) and NumberFlow lite bundled by `tools/motion/js/build-counter.mjs` (pinned esbuild 0.28.2, IIFE, es2019; bare imports resolved as the import map used to: `number-flow/lite` → `vendor/number-flow/lite.mjs`, `esm-env/browser` → `true.js`, `esm-env/development` and `esm-env/node` → `false.js`). Generated and committed; CI runs `--check`. Enqueued by `Assets::enqueue_engine()` with the engine, only when `Marker::engine_families()` holds `counter` (settled counters of the first screen do not count), always in the canvas, then injected by the loader after the first paint like the other scripts. The engine finds `window.lumiaMotionCounter`, or waits for `lumia-motion-counter-ready` (3 s), so the order in which they run does not matter.
- **Why not script modules (2.2.0 used them):** nginx, up to 1.31 at least, has no MIME type for `.mjs` in its `mime.types` and serves it as `application/octet-stream`; browsers refuse a module script with a non-JavaScript type. On every site of the agency no counter rolled (they stayed as written); the local Docker copy runs Apache, which knows `.mjs`, so nothing showed there. The script-module version also needed the import map printed in the footer after the Bricks popups (`order_module_printing()`, `withhold_counter()`): all gone. The vendor `.mjs` files stay in `vendor/` byte for byte (sources and licenses) and ship unused; nothing requests a `.mjs` (e2e `counter`).
- **Loading:** nothing is loaded on a page without an effect. GSAP, ScrollTrigger and the engine load in the footer (priority 19, after Bricks renders popups at 10) only when the page uses an effect the engine plays (`Marker::engine_families()`: load animations and settled elements do not count), SplitText only for text effects. An underline-only page loads no engine (the underline is CSS; Lenis may still load, it is on every page when enabled). A 3000 ms safety in the `<head>` removes the pre-hide even if the engine never runs.
- **Nothing of the module before the first paint (public pages):**
  - **Styles inline.** `motion.css` (and `lenis.css` when smooth scroll is on) are printed in `<style id="lumia-motion-inline-css">` / `<style id="lumia-lenis-inline-css">` in the head, through handles with no file (`wp_register_style( $handle, false )` + `wp_add_inline_style()`), read once per request. The file read is the one that used to be linked: the release zip minifies `motion.css` in place, so production prints the minified styles; `lenis.css` is a vendor file and is printed as shipped. Same in the canvas, deliberately (one code path; nothing there is measured); the main builder window keeps `motion-builder.css` linked.
  - **Engine after the first paint.** The scripts are still enqueued exactly as before (same handles, conditions, dependencies, URLs with `?ver=`); on a public page `Assets::print_loader()` then takes the queued Motion handles, orders them with their dependencies as WordPress would, applies `script_loader_src`, prints their inline `before` data (`window.lumiaMotionConfig`, `window.lumiaMotionScroll`) and an inline loader with the ordered URLs as JSON, and dequeues them: no `<script src>` of the module in the HTML. The loader waits for `DOMContentLoaded`, then for the first paint entry (`PerformanceObserver`, type `paint`, buffered: `first-paint`, or `first-contentful-paint` in browsers that only have that one; two `requestAnimationFrame` where paint timing is missing; 1000 ms at most, for a tab opened in the background; and 100 ms after two frames, `LOADER_FRAME_GRACE_MS`, for a browser with only `first-contentful-paint` (Safari, Firefox) on a first screen with nothing contentful, which waited the whole second before), then appends the scripts with `async = false` (fetched in parallel, run in order) and the same ids as WordPress (`lumia-motion-js`…). A script that fails to load adds `lm-ready` at once: the page is shown without waiting for the 3 s safety (a script that loads but never starts the engine still waits for it). Smooth scroll starts a frame or two later than before. Two frames alone were the first idea and were not enough: Chrome's paint entry carries the time the frame was presented, measured 2 ms after the second frame callback had already injected the counter module (e2e).
  - **Why:** since the load animations are pure CSS, the first frame needs no script. Chrome painted the module page at the same time as a page without animation (observed LCP 317 ms home, 217 ms contact), but Lighthouse's simulated throttling (Lantern) charges every request started before the observed LCP, and the CPU time of those scripts on its 4x slower CPU, to its LCP estimate: as deferred tags, the 7 scripts (85 KB) started at 267 to 273 ms, and the two render-blocking stylesheets before them.
  - **What the loader cannot carry falls back to WordPress's tags** (`Assets::loader_unsafe()`): an `after` inline script, `wp_localize_script()` data (kept as `data`) or a `script_loader_tag` change (attributes, `type`, CSP nonces; the filter is run on a plain tag of each handle, and a filter that targets other handles returns it as is) on any handle the loader would inject. The loader prints only the `before` data and no tag, so it used to drop them silently; now the page keeps the deferred tags, as before the loader existed. A handle WordPress already printed (`$scripts->done`, a dependency of a script of the head) is not injected again.
  - **Builder canvas:** unchanged, the scripts are printed by WordPress (no loader): Bricks calls the builder hooks of the canvas at its own time, and nothing there is measured.
- **Late start:** the engine can start after the safety has shown the page (a slow phone: `DOMContentLoaded` plus the font wait), or after the load when a "delay JS until interaction" optimiser holds the scripts. Its first build made the entrances of what was on screen, so content the visitor was reading vanished and replayed. Now the first build is quiet (on-screen items final, below-the-fold items still animate) when `<html>` already has `lm-ready` or has no `lm-js`, and the head script adds `lm-js` only while `document.readyState === 'loading'`: run late, it pre-hides nothing. An element without a box (`display: none`, the content of a closed popup) is neither on screen nor above it: its all-zero rectangle used to read as "on screen", so a quiet build settled it and it lost its entrance when shown later.
- **Entrances end at the author's opacity and filter**, read by `read()` before the engine writes anything (`authorEnd()`), as the CSS load animation does (its keyframes give the start only). They used to end at `opacity: 1` and `blur(0)`, then jump to the author's values when the inline styles were cleared. The blur is composed with the author's filter (`blur(12px) grayscale(1)` to `blur(0px) grayscale(1)`), so both ends have the same functions. For that read, `lm-ready` is added **before** the first build, in the same task: nothing is painted between the end of the pre-hide and the start states the build writes. A rebuilt item that is pending or playing keeps the values read the first time (its element carries the engine's state); a done or final one is read again (an opacity edited in the builder panel). An element whose own opacity is 0 stays at 0: the author's value is kept, even that one.
- **Bricks content events:** the build runs at once (Bricks inserts the results and sends the event in the same task; built later, the new entrances painted in full, then vanished and came back), and only the refresh of every trigger (`ScrollTrigger.refresh()`) is grouped, 50 ms after the last event of one change (a page, then its results).
- **Words and letters end at `bottom 45%`** (was `top -120%`). Two consequences: a site whose Motion settings page was saved before keeps the stored `top -120%` (save it again with the new values, or reset them); an element that sets only the End height now measures it from the bottom edge (a hand-tuned `20%` meant `top 20%`, it now means `bottom 20%`: clear it or set the edge too). With the bottom edge, the letter being revealed moves on screen from the start height (98%) to the end height whatever the length of the text: the last one lights up just above the middle, on a phone (9-line title) as on a desktop (4 lines). Measured on the lab home: the hand-tuned `top 20%` put that last letter at 43% of a 986 px desktop screen but at 61% on a 390 × 844 phone.
- **Content is never left hidden:** an entrance whose start the page can never scroll to (footer CTA at `top 60%`, mobile address bar collapsing) plays when the page end is reached; scrubs are clamped to the page end; every build error settles the element in its final state.
- **`html { scroll-behavior: smooth }` broke reloads** (the former snippet forced the page back to the top): the stylesheet sets `scroll-behavior: auto !important`. Entrance elements also get `overflow-anchor: none`: Chrome's scroll anchoring followed the 20 px start offset of a blur-up and landed 19 px off after a reload. Side effect: those elements are not used as scroll anchors.
- **Lenis** loads on every public page when enabled (never in the builder, never under `prefers-reduced-motion: reduce`), driven by the GSAP ticker when GSAP is present, by a loop of `motion-scroll.js` otherwise. Not `autoRaf`: Lenis's own loop runs every frame for as long as the page is open (measured in Chrome, page untouched for 10 s: about 110 ms of tasks and 60 frames a second, about 1 % of a desktop core). The loop of `motion-scroll.js` stops 10 frames after Lenis stops scrolling and starts again on `virtual-scroll` (wheel, touch), a native `scroll` (keyboard, scrollbar), `scrollTo()` (anchor clicks call it through the instance) and `start()`; measured again: 0 frames while idle, the same smoothing as before. On waking it sets `lenis.time = 0`: `Lenis.raf()` steps by the time since its last frame, and after a sleep that step made the smoothing jump straight to the target. With GSAP the ticker is left as it is (other things depend on it). It stops while a Bricks popup is open or while Bricks puts `no-scroll` on the body (off-canvas, mobile menu), and stands down if the former snippet is still active: at start, or whenever its global appears later. This file is injected after the first paint, often after the `load` event, so the `load` listener it relied on alone never fired; the global is watched instead (an accessor on `window`: the first assignment stores the value as a plain property again, so the snippet runs as it always did, and Lenis stands down on the next tick). Popups and off-canvases get `data-lenis-prevent` at load; menus (`.brx-nav-nested-items`, `.bricks-mobile-menu-wrapper`) only while the page is locked, and lose it on unlock: on desktop the first one is the bar of the nested nav (and its mega menu), and marked at load it let the browser scroll natively under Lenis whenever the wheel was over it. Anchors are offset by `--navbar-height` (measured, so `clamp()` and `rem` work); a cross-page anchor is corrected once after `load`. A root `scroll-padding-top` would be added twice by Lenis: do not combine it with `--navbar-height`.
- **Text effects and screen readers:** headings keep SplitText's `aria-label`; other elements get a visually hidden copy (styled inline, so a "remove unused CSS" optimiser cannot reveal it, and not selectable) next to a split box hidden with `aria-hidden` (ARIA 1.2 forbids `aria-label` on a paragraph). Elements containing a link or a control keep their pieces readable. `lines` restores the original HTML at the end; scrubs stay split while the page is open.
- **Counter (NumberFlow):** a single run of digits in a single text node is animated; the text is rebuilt from the parsed format and refused unless it gives back the original byte for byte ("24/7", "007" are never touched). The digits roll with NumberFlow 0.6.2 (lite build), embedded as is: a home-made roll left traces of neighbouring digits and shifted at the end. `motion-counter.mjs` uses only its public API (`define('lm-number-flow', …)`, `formatToData`, `canAnimate`, `data`, `animated`, the timings) with an Intl formatter whose group and decimal parts are replaced by the separators of the page, so the format is the written one (no grouping added: `2024` never gets a separator).
  - **Mount and end:** the text node is replaced by `<lm-number-flow>` at the start value while the counter waits for its start, and the element **stays** once the value is written: going back to the text shifted the number by a few pixels. `final` / `kill` (destroy, builder change, reduced motion switched on) put the original text node back.
  - **Duration and curve:** duration of the effect × tempo (`tweenDuration`), curve as CSS `linear()` from `cssLinear()` (snappy and bouncy are already smooth for a counter, it never passes its value), `linear`, or the custom `cubic-bezier()` when both its y values stay in [0, 1] (`core.counterEase()`). A custom curve with y1 or y2 outside [0, 1] would show a value past the written one (or below the start) and is replaced by `smooth`, not clamped (clamping makes another curve than the one typed); `?lmDebug` says so. Passed to `transformTiming` and `spinTiming`; `opacityTiming` is NumberFlow's.
  - **Width (`--lm-counter-width`, site default in the reference values):** `auto` (default) widens as digits appear; `fixed` formats every value with the integer digit count of the final one (`minimumIntegerDigits`: "0 000" before "1 250") and `tabular-nums` on the element, so its width never changes (checked on every frame by the e2e scenario). The final number is a little wider than in proportional digits.
  - **No layout shift:** NumberFlow pads its number for the fade mask, which made the line taller (61.6 px to 84 px measured). `motion.css` gives the space back (`lm-number-flow { line-height: inherit; vertical-align: top; margin-block: calc(-2 * round(nearest, calc(var(--number-flow-mask-height, .25em) / 2), 1px)); }`); the e2e scenario checks a constant height on every frame, in both widths. The former `[data-lm~="counter"] { font-variant-numeric: tabular-nums }` rule is gone: dynamic width keeps the font's own digits.
  - **Accessibility and crawlers:** screen readers always get the written value, never the start value. NumberFlow names its element after the value it shows (`ElementInternals`, role image), which is the start value ("0") until the counter plays, so the engine sets `aria-hidden="true"` on `<lm-number-flow>` and puts a visually hidden copy of the written text (`.lm-sr`) next to it: that copy is what assistive technologies read, from the mount on (e2e: the ARIA snapshot of every counter equals the one of the plain page while pending, while playing and at the end). The copy also keeps the number in `innerText`: NumberFlow's digits live in the shadow DOM, which `innerText` leaves out (measured empty on a mounted counter), so a rendering crawler would have lost the number. The copy is inline-level (`display: inline-block`, no width): an absolute box counts as a block in `innerText`, which read "350\n projets". The served HTML always holds the number as written. (The design spec planned to rely on NumberFlow's own label; changed for the pending state.)
  - **Fallbacks:** `prefers-reduced-motion`, `canAnimate` false, or the adapter absent after 3000 ms (blocked file, no module support): the text stays as written, no element is mounted.
  - **Style (`--lm-counter-style`, site default `counter_style` in the reference values):** `odometer` (default, everything above) or `count`, a classic count from the start value to the written one (1, 2, 3 … 620). Resolved like the width (`core.resolve()`: typed on the element, else the site value; an unknown keyword is `odometer` with a `?lmDebug` warning; a site saved before the setting existed gets `odometer` from the recursive merge over the defaults, and the JS also falls back to `odometer` when the key is missing). The count is written by the engine itself (`countAdapter` in `motion.js`, same `mount` / `play` / `reset` interface as `window.lumiaMotionCounter`), so it never waits for `motion-counter.js` and works where NumberFlow cannot animate; the bundle is still enqueued on a page with a counter, since the style may come from a class and is only known in the browser.
    - **Each frame** writes `prefix + core.formatCounter(value) + suffix`: the parser's own formatter, so separators, decimals (always the count of the written value), prefix and suffix are those of the page, and the last write is the parsed value itself, which `parseCounter()` guarantees gives back the text byte for byte (never a stray 619). The text is written only when it changes.
    - **Curve and timing:** `core.counterProgress()` is the curve of `counterEase()` as a function (the exact spring of which the odometer's `linear()` is the approximation, the custom curve when its y values stay in [0, 1], `linear`), over `tweenDuration`, after `delay`, on `requestAnimationFrame`. A hidden tab runs no frame: a timer writes the value 150 ms after the expected end, as the odometer does. That timer is armed again on the first frame: armed only when the delay ended, a first frame late by more than the margin (busy page) made it jump to the final value mid-count.
    - **Element:** an `<lm-count>` element (a custom tag, never defined, like `<lm-number-flow>`: a theme rule such as `.stat__value span { display: block }` aimed at the suffix of a stat would have restyled a `<span>`) replaces the text node, with `tabular-nums` (the number does not jitter while it changes) and the digits in an open shadow root, like NumberFlow's: `innerText` leaves them out, so a crawler reads the number once, from the `.lm-sr` copy, not "620620" (measured in Chrome). Without `attachShadow` the text stays as written. It is `aria-hidden` and stays once the value is written; `final` / `kill` put the original text node back. Unlike the dynamic odometer, the written number stays in tabular digits once counted: a few pixels wider or narrower than the plain text in a font with proportional digits (measured: "11 000" in Candara, 159 px written, 175 px counted).
    - **Fixed width** pads the integer part with zeros to the digits of the written value (`formatCounter(value, fmt, digits)`: "0 005" on the way to "1 250"), as the fixed odometer does. `tabular-nums` does nothing in a font without the `tnum` feature (Georgia): the width changed on every frame (measured: 211 widths between 308 and 361 px for "+ 36 000 €"). The ten digits are measured in the shadow root (`offsetWidth` of ten of each, so the transform of an entrance still at its start state does not count), at mount and again when the delay ends (the web font has usually arrived by then); when their widths differ, each digit is written in an inline-block box of the widest digit's width, in `em` (a fluid `clamp()` font size keeps the boxes right), so the width never changes. The boxed run is `white-space: nowrap`: inline-block boxes are break opportunities, and "1250" could wrap as "12 / 50", which the written text never did. The prefix and suffix are separate text nodes and wrap as before.
- **Builder:** no pre-hide and no ScrollTrigger in the canvas; everything shows its final state; a change made in the panel replays the effect once (setting "Replay on change"), except under reduced motion. Elements added during the session have no `data-lm` and are found by their computed `--lm-effect`.
  - **Changes inside a playing element** (the engine's own split text or counter digits, or an edit of a child made during the play) cannot be told apart: `motion-builder.js` reads them once the play is over (checked every 250 ms) instead of dropping them. A child edited while its container played used to be ignored until the next change.
  - **Not replayed:** a change to an element above the visible part of the canvas (it would play off screen; the Replay button of the panel plays it on demand).
  - **`_lmTempo: exact`** (content saved during the first trials): the front reads it as `custom`, but the Tempo select of the builder shows no selection, since `exact` is not one of its options. Pick a tempo again and save to clear it.
- **Panel** (`Controls::definitions()`): six sections in this order, each opened by a separator: Effect (effect, help with the Replay button and the "Show markers" checkbox), Trigger, Timing, Feel, Effect settings, Underline. Bricks shows a group's controls in array order: a new control goes in its section's method. Each number field carries a sentence and its unit (`description`) and a static placeholder, the reference value of `fade`, else of the first effect with that setting.
- **Empty Easing and Tempo fields** show the site value as placeholder ("Smooth (site default)"), read from `lumia_module_motion` when the panel is built.
- **`motion-panel.js`** (main window only, `Assets::enqueue_scripts()`) talks to the canvas engine through `window.lumiaMotion` of `iframe#bricks-builder-iframe` (same origin): `replay(id)`, `markers(on)`, `inspect(id)`. The selected element comes from the builder state: Bricks 2.4.2 mounts a Vue 3 app on `[data-v-app]` and exposes its reactive state as the global property `$_state` (`root.__vue_app__.config.globalProperties.$_state.activeElement.id`; `$_watch` is exposed too and is used to follow the selection, the class and the breakpoint, since Vue may patch the same inputs in place).
  - **Placeholders:** an empty number field shows what the element inherits (its class, else the site value of its effect), from `inspect(id)`. Time values are given before the tempo factor, as a field holds them: a "fast" element with a class stagger of 0.15 shows 0.15, not 0.1125. Limit: while a class is being edited, the placeholders still show the selected element's values.
  - **Markers:** "Show markers" is a preference of the browser (`localStorage.lmMotionMarkers = '1'`), read by the canvas engine when it starts; never saved in the page, never on the public site (`?lmDebug` stays there). In the canvas, where nothing follows the scroll, the engine creates marker-only triggers with GSAP's own markers, the set `?lmDebug` shows on the front: per item the `start` and `end` markers on the element and the `scroller-start` / `scroller-end` lines on the viewport, drawn again on every read of the page (not only when an item changes: a layout edit, such as a padding or an element added above, moves the elements without changing any signature, and the markers stayed where they used to be). A scrub gets its own end; a one-shot effect (entrance, text, counter) is created without an end, exactly as the engine creates its trigger, so the end shown is ScrollTrigger's default `bottom top`, where that trigger kills itself (`once`). Before, a one-shot effect got `end = start` and a transparent end color: only the start lines were visible, which did not match the front's debug markers. No `ScrollTrigger.refresh()` after drawing them: it adds a measuring `<div>` to the body, which `motion-builder.js` took for a change of the page and answered with a new scan. The builder script also ignores the `gsap-marker-*` nodes.
  - **Checkbox:** set from the preference once, when it first renders (`data-lm-synced`): setting it on every render undid the click, because Bricks re-renders during the click, before the `change` event.
- **Group icon:** the group declares the Bricks icon `star` (`assets/svg/builder/star.svg`), shown in its title; `motion-builder.css` hides that SVG (`visibility`, to keep the box) and draws the Lucide `sparkles` (lucide-static 1.34.0, the official file as is, base64 in a CSS mask) over it.
- **Rail shortcut:** the left rail of shortcuts of the element panel (`#bricks-panel-element-quick-access`, "quick access") is a Vue component whose list is fixed in Bricks 2.4.2 (the `shortcuts` computed in `main.min.js`: content, `_layout`, `_typography`, `_background`, `_border`, `_gradient`, `_shapes`, `_transform`, `_css`, `_attributes`); there is no plugin API. `motion-panel.js` appends its own `<li class="lm-rail-motion">` after the last Bricks item, with Bricks' markup (`data-balloon` = the group title read from `$_getElementConfig(name).controlGroups.lm_motion`, `data-balloon-pos` copied from a Bricks item, a `.bricks-svg-wrapper` holding the sparkles mask of the group title, sized and scaled like the Bricks icons). No `.index` badge: the digit shortcuts address Bricks' list by position. A click sets the state Bricks' `setActivePanelGroup()` sets for a style group (`$_clearSearchControls()`, `activePanelGroup = 'lm_motion'`, `activePanelTab = 'style'`, `showHideElement` / `showConditions` / `showInteractions` = false, `elementQuickAccessIndex = -1`); the component instance itself is not reachable (no `__vueParentComponent` in the production build). `active` follows the tab and group, `has-settings` any `_lm*` key on the class being edited, else on the element (a cheap version of Bricks' `controlGroupHasSettings()`), through `$_watch`. Vue drops the foreign item whenever it renders the list again (a new `<ul>` on every `renderKey` change, so on every selection): the item is put back from the builder's `MutationObserver` (childList only; the insertion wakes it once and the next pass finds the item in place, setting classes never wakes it). The rail itself is unmounted when no element is selected, which is why the body is observed rather than the rail. **Fragile by design:** it depends on Bricks internals (the rail id, its `<ul>`, the `$_state` keys); when they change, the item is simply absent, the code fails silently (`try`/`catch`, no console output).

## Migrating a site from the snippet

1. Back up the database. Install Lümia Tools and enable Motion. Activation creates no class: new sites pick effects in the Motion tab of each element. `wp lumia motion classes --user=<admin>` creates the missing `lm-*` classes in a "Motion" category on request, except where the `sk-*` equivalent exists; the user must be an administrator, and is only asked for when there is a class to create (listing needs none).
2. `wp lumia motion migrate --user=<admin>` (dry run, writes nothing): lists the `sk-*` classes to rename, conflicts (an `lm-*` class already exists: the `sk-*` one is left alone), the pages and elements using them, and the CSS to check.
3. `wp lumia motion migrate --apply --user=<admin>`: renames each class in place (**same ID**, so no page content is rewritten), moves it to "Motion", rewrites the class's own custom CSS, then regenerates the Bricks CSS files. Running it twice changes nothing.
4. Right after: fix the `.sk-*` selectors the report lists in element, page, template or global custom CSS — they stop matching at `--apply`, the compatibility setting does not bring the old names back. Deactivate (or delete) the "SK Motion" snippet, purge the page cache, check the site.
5. What the report lists as "kept working" goes on working while the compatibility setting is on: former names typed in a "CSS classes" field, the `--sk-hover-underline-*` variables (read as a fallback by the underline of the renamed class), and the selectors of classes that keep their name (conflicts). Replace them at leisure.
6. When the Compatibility tab reports nothing left, turn off "Former class names".

The scan ignores revisions, trashed posts and auto-drafts; published FluentSnippets files are reported, never modified.
