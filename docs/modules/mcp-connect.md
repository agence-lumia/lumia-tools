# MCP Connect module

`includes/Modules/McpConnect/` + `assets/admin/js/modules/mcp-connect.js` / `assets/admin/css/modules/mcp-connect.css`. Each site becomes an OAuth 2.1 authorization server for its own MCP Adapter endpoint, so it can be added to Claude (claude.ai, Desktop, Cowork, Claude Code) as a custom connector: **Settings > Connectors > Add custom connector > paste the MCP URL > Connect > approve in WordPress.** No proxy, no application password, no snippet (issue #46).

The module does not provide MCP itself: the [MCP Adapter](https://github.com/WordPress/mcp-adapter) plugin (0.7 or later, checked on 0.7.1) serves the abilities on `/wp-json/mcp/mcp-adapter-default-server`. MCP Connect only answers the question the Adapter leaves open, "who is this request?", with a Bearer token. Application passwords keep working side by side.

Classes:

- `Discovery`: the two `/.well-known/` documents, the `401` challenge, the early boot of the Bearer filter, route detection.
- `BearerAuth`: the access token on the MCP route, and on it only.
- `AuthorizationServer`: REST endpoints under `lumia-mcp/v1` (`/authorize`, `/token`, `/revoke`, `/register` when DCR is on, `/ping` for Site Health).
- `ConsentPage`: the consent screen in wp-admin and its `admin-post.php` handler.
- `ClientRegistry`: CIMD resolver (with the SSRF guards) and DCR.
- `Tokens`, `Connections`, `Store`: the three tables.
- `Agent`: role `lumia_mcp_agent`, the `claude-mcp` account, permission presets.
- `SiteHealth`: discovery, `Authorization` header and environment tests.
- `Security`: client IP, rate limiter and no-store headers shared with the Security module.
- `Module`: settings, hooks, admin screen, AJAX.

## The flow

1. **Discovery.** Claude posts to the MCP URL without a token. The Adapter answers `401`; `Discovery::challenge()` adds `WWW-Authenticate: Bearer resource_metadata="…", scope="mcp"`. Claude fetches the protected resource metadata (RFC 9728), then the authorization server metadata (RFC 8414) at `/.well-known/oauth-authorization-server`.
2. **Authorize.** The browser opens `/wp-json/lumia-mcp/v1/authorize`. The client is resolved (CIMD, below) and the `redirect_uri` checked against it; until both pass, errors are an HTML page, **never a redirect** (redirecting to an unchecked URI would make the endpoint an open redirector). After that, errors go back to the client with `error`, `state` and `iss`: `response_type` must be `code`, PKCE `S256` only (`plain` refused), `resource` (RFC 8707) required and equal to the MCP URL, scopes limited to `mcp` and `offline_access`, trusted publisher when the setting asks for it, module not paused. The request is stored as a `request` token (10 minutes) and the browser goes to `admin.php?page=lumia-mcp-consent&request=…`.
3. **Consent in wp-admin.** A wp-admin page rather than a front-end one: the sign-in, custom login slug of the Security module included, comes for free through `auth_redirect()`, and the decision is an ordinary `admin-post.php` form with a nonce. The handler consumes the request atomically (a double click, a second tab or a replayed POST cannot mint two codes), re-checks the settings (they may have changed since `/authorize`), creates a `pending` connection and redirects with a 60-second code, `state` and `iss` (RFC 9207).
4. **Token.** Claude exchanges the code at `/token` (`application/x-www-form-urlencoded`) with its PKCE verifier. The connection turns `active` there, and only there: a code never exchanged leaves no connection behind (the purge deletes pending rows after a day), and the Activity Log records the authorization at that moment. An access token (1 h by default) and a refresh token (30 days, sliding) are returned.
5. **Bearer on the MCP route.** `BearerAuth` turns the access token into the connection's acting user on `determine_current_user`. The Adapter's own transport check (`current_user_can( 'read' )`) then lets the request through.

Refresh rotates: every use returns a new refresh token and marks the old one used. A used refresh token presented again means two parties hold it: the whole connection is revoked (OAuth 2.1 for public clients) and logged. A code presented twice is a replay too: its connection is revoked, which also deletes any token issued from it. Everything is checked **before** a code is consumed, so a request without the right verifier cannot burn the legitimate client's code. A code or a refresh token naming another `client_id` is refused (`invalid_grant`) before the reuse test, so it cannot revoke someone else's connection: codes travel in URLs (browser history, proxy logs, Claude Code's loopback callback), and whoever reads a used one must not be able to kill a live connection with it. Only a replay carrying the code's own `client_id` revokes.

`/token` and `/revoke` answer RFC 6749 §5.2 JSON errors. Claude only recovers on those codes, and `invalid_grant` makes it drop the connection: a pause or a rate limit therefore answers `invalid_request`, never `invalid_grant`. `/revoke` (RFC 7009) always answers `200`, unknown token included; a refresh token revokes its connection, an access token is deleted alone.

## Storage

Three tables, `{prefix}lumia_mcp_clients`, `lumia_mcp_connections` and `lumia_mcp_tokens`, schema versioned like the Activity Log (`Store::SCHEMA_VERSION`, option `lumia_mcp_schema`, `maybe_install()` on every load because a module enabled by a configuration import skips `on_activate()`).

- **Tables, not options or transients**: a token is looked up by its hash on every MCP request (an indexed column), and the issue forbids keeping any token, even hashed, in an option or a transient.
- **Hashed tokens.** Every secret (request id `lmc_rq_`, code `lmc_ac_`, access `lmc_at_`, refresh `lmc_rt_`) is a prefix plus 256 random bits; only its SHA-256 reaches the database. A plain hash, not a password hash: the secret already carries 256 bits, and the hash must be an exact indexed key. The lookup re-checks with `hash_equals()` (the index comparison is neither constant-time nor case-sensitive). The prefixes make a leaked token greppable; a value without the right prefix is refused without a query. Tokens are never logged, never in options, transients or URLs, except the request id and the code, which travel in redirect URLs because that is the protocol.
- **Atomic consume.** Codes, refresh tokens and authorization requests are consumed with `UPDATE … SET used = 1 WHERE id = %d AND used = 0`, and the affected-row count says who won. Two requests racing with the same code or refresh token both read `used = 0`; only one changes the row. Boilerplate runs Redis Object Cache: a check-then-delete through transients would be racy there.
- **Connections** are the unit the admin sees and revokes: `pending` → `active` → `revoked`. Revocation is a conditional `UPDATE` (only one of two concurrent paths fires the action) and deletes the tokens at once; the row stays 90 days for the list (30 days shown) and the Activity Log. `last_used_at` is written at most once a minute per connection, the throttle sitting in the `WHERE` of the same `UPDATE`.
- **Values cut to the column width** before the `INSERT` (strict SQL mode would make the whole insert fail), by characters since the tables are utf8mb4.
- **`client_id` is limited to 191 characters**: the unique index covers 191 characters (utf8mb4 limit of old MySQL); two longer URLs sharing that prefix would collide. The SQL comparison is case-insensitive under the usual collations, so a row is only reused when the id matches byte for byte.
- **Daily purge** (`lumia_mcp_connect_purge`, scheduled in `init()`): tokens expired for more than a day (the day of grace keeps a replayed code or refresh token recognisable as a replay rather than an unknown token), pending connections older than a day, revoked connections older than 90 days, DCR clients unused for `dcr_purge_days` (unless a live connection uses them), CIMD cache rows expired for more than 30 days. `DELETE … LIMIT 2000` in batches, 50 at most: a single large delete locks the token table and every MCP request waits behind it.

## Clients: CIMD first

The MCP spec (2026-07-28) asks for Client ID Metadata Documents: the `client_id` is an HTTPS URL whose JSON describes the client. Fetching it means making the site issue a request to a URL chosen by whoever opens `/authorize`, i.e. anyone. The guards, in order, before any byte leaves the server:

1. **URL shape**: `https`, no userinfo, no fragment, port absent or 443, a path beyond `/` without dot segments, a fully qualified DNS name (IPv4 and IPv6 literals and single-label names such as `localhost` refused: an IP literal would skip the resolution check).
2. **Trusted publisher** (default on): a host outside `lumia_mcp_connect_trusted_publishers` (default `['claude.ai']`) is refused with a clear message naming it, **before any fetch**.
3. **Cache**: a fresh row in the clients table is used as is. TTL from `Cache-Control: max-age`, clamped to 5 minutes to 1 day (the floor protects the budget from `max-age=0`), one hour without it.
4. **Negative cache**: a failing URL is not fetched again for 60 seconds, so reloading the authorize link does not spend the budget.
5. **Global budget**: 20 fetches per minute for the whole site (fixed window in a transient, approximate on purpose). Without a cap the public endpoint would turn the site into a request relay.
6. **Resolution**: A and AAAA records; **any** non-public address refuses the host (one private record is enough, the resolver could hand it out at connection time). `filter_var()` ranges vary between PHP versions and do not look inside IPv6 addresses embedding an IPv4 one, so carrier-grade NAT, documentation and benchmark ranges, IPv4-mapped (`::ffff:`), NAT64 and 6to4 are checked explicitly, with the embedded address checked in turn.
7. **Pinned request**: `CURLOPT_RESOLVE` set through a one-shot `http_api_curl` action pins the connection to the checked address. It is the only way to pin with the HTTP API: without cURL the fetch is refused (the request would resolve again, a DNS rebinding window), and an answer that did not go through the pin is discarded. `wp_safe_remote_get()` with 5 s timeout, no redirect, 64 KiB limit, `sslverify`. `limit_response_size` truncates silently: a body that fills the limit is refused rather than parsed.

The document must carry `client_id` equal to the URL, non-empty `redirect_uris` (absolute `https`, or loopback `http`), and `token_endpoint_auth_method` absent or `none` (public clients only). Unknown fields and unsupported grant types are **ignored, never rejected**. `logo_uri` and `client_uri` are kept only in `https`.

**Redirect URIs** are exactly those of the fetched document, matched as exact strings, except loopback URIs (`localhost`, `127.0.0.1`, `[::1]`), where the port is ignored (RFC 8252 §7.3: Claude Code listens on an ephemeral port); host, path and query must still match. No list of Claude callbacks is hard-coded: the day Anthropic adds `claude.com`, its document will say so.

### What Claude actually sends

Captured by the `/authorize` spy of the spike on boilerplate (claude.ai web, 2026-10-26) and read from the published client metadata documents:

| Client | `client_id` (CIMD URL) | `redirect_uris` in its metadata | Requested `scope` |
|---|---|---|---|
| claude.ai (hosted apps) | `https://claude.ai/oauth/mcp-oauth-client-metadata` (`client_name` "Claude") | `https://claude.ai/api/mcp/auth_callback` only | `mcp offline_access` |
| Claude Code | `https://claude.ai/oauth/claude-code-client-metadata` (`client_name` "Claude Code") | `http://localhost/callback`, `http://127.0.0.1/callback` | — |

- Both documents declare `token_endpoint_auth_method: none`. The hosted one also lists the `urn:ietf:params:oauth:grant-type:jwt-bearer` grant (Enterprise managed auth, out of scope): the authorization server must ignore grant types it does not support rather than reject the client.
- `https://claude.com/api/mcp/auth_callback` is **not** in use yet, hence the rule above (accept exactly the `redirect_uris` of the fetched document).
- Claude added `offline_access` to the challenge's `scope="mcp"` on its own, because the authorization server metadata lists it.
- The claude.ai "Add custom connector" dialog read the discovery documents before connecting: it showed "Sign in now" and "Use Claude's published identity (CIMD)" as **Detected**. It also lets a user add up to four static request headers sent alongside the OAuth token.

### DCR

Dynamic Client Registration (RFC 7591) is Claude's fallback when CIMD is not advertised. It is **off by default**; the `registration_endpoint` is only advertised when it is on, because Claude tries it whenever it is listed. When on: 10 registrations per IP and per hour (counted on every attempt, valid or not: the counter bounds the work an anonymous caller causes, not only the rows), plus the Security lockout; `redirect_uris` validated like a CIMD document, `none` auth only, `grant_types` within `authorization_code` / `refresh_token`. Client ids are `lmc_cl_` + 32 hex. A DCR client is **never trusted** (anyone can register one under any name), so it is refused while "Trusted publishers only" is on; the settings screen says so. Turning DCR off refuses every DCR client at `/authorize`, not only new registrations.

## Bearer on the MCP route

- **Audience.** The token is only looked up when the raw request targets the MCP route. The same token on `/wp/v2/users/me`, `/wp/v2/settings` or anywhere else stays anonymous: MCP Connect gives no general REST access.
- **Audience at dispatch time, outermost dispatch only.** `rest_pre_dispatch` @999 (`BearerAuth::restrict_dispatch()`) refuses any route but the MCP one for a token-authenticated request, whatever way WordPress chose it (POST `rest_route`, method override, `/batch/v1`). It does **not** apply to the dispatches nested in the MCP call: `rest_pre_dispatch` fires for every `WP_REST_Server::dispatch()`, `rest_do_request()` included, and the authenticated connection stays set for the whole PHP request. A first version guarded every dispatch, and any ability wrapping a REST endpoint (`rest_do_request( '/wc/v3/products' )`, the WooCommerce-style abilities a shop needs) failed with `401 invalid_token` through a token while it worked with an application password. So `rest_request_before_callbacks` records the outermost MCP request when its callbacks start, and `rest_request_after_callbacks` (applied after every `before_callbacks`, error paths included) clears it, with `rest_post_dispatch` on the same request as a fallback. A dispatch while it is recorded passes (it runs as the same user, under the same capability checks, so it gives the agent nothing a PHP ability could not already do); a dispatch before or after it (a plugin preloading a route, `_embed` links) is still refused. The bench fixture `e2e/nested-rest` checks it.
- **`determine_current_user` @30**, after the core cookie (10) and application-password (20) handlers: a request they authenticated is left untouched.
- **A wrong Bearer answers `401 invalid_token`** from `rest_authentication_errors` @90 rather than falling back to an anonymous request. The outcome is memoized: whichever of the two hooks runs first does the lookup, once.
- **Rate limiting.** Only **unknown** tokens count as failed attempts in the Security limiter. An expired token is the normal case (Claude refreshes on the `401`), and the hosted Claude apps share one egress range: counting it would lock Claude itself out. `log_successful_login()` is never called: it would wipe the IP's failed login-form attempts. The limiter is built from `lumia_module_security` even when Security is inactive (same thresholds, same IP source, same per-IP transient, so a lockout earned on the login form holds on `/token` and the other way round), and respects `rate_limiting = false`.
- **Acting user re-checked on every request.** An agent connection must still point to a user holding the agent role (an account changed by hand does not inherit the connection); an "act as me" connection must still belong to an approver (a demoted administrator loses it).
- **On hold.** The filter is added at file load, before `FromSkmt::on_hold()` can be known: `BearerAuth` asks `Plugin::is_on_hold()` and refuses, so a site still running SKMT or with a stopped migration authenticates nothing.

## Hook timing pitfalls

- The Adapter never reads the `Authorization` header itself. Its transport `permission_callback` is `current_user_can( 'read' )` (filter `mcp_adapter_default_transport_permission_user_capability`) when no custom callback is given, so authenticating a user on `determine_current_user` is enough. Its sessions (`Mcp-Session-Id`) live in that user's meta: they work unchanged for a Bearer user.
- The Adapter creates its servers on `rest_api_init` @15 and registers the route @16. The authentication hooks do not depend on that order: `determine_current_user` runs whenever the current user is first needed, `rest_authentication_errors` and `rest_post_dispatch` around the dispatch.
- **The filter is added at file load, not on `plugins_loaded` nor in `Module::init()`** (`Discovery::boot()`, called from `lumia-tools.php`, which only reads the raw module flag in the autoloaded `lumia_settings`). `_wp_get_current_user()` caches its first result for the whole request, an anonymous `WP_User( 0 )` included: a plugin resolving the user on `plugins_loaded` before Lümia's callback (priority below 10, or same priority and a folder sorting before `lumia-tools/`) locked every MCP call to `401` whatever the token. Core's cookie and application-password handlers have no such problem because `default-filters.php` adds them before any plugin loads. Checked on the bench with a plugin resolving the user on `plugins_loaded` @1.
- **Route detection reads the raw request URI**, not the parsed REST route. Any plugin calling `wp_get_current_user()` on `init` (or earlier) resolves and caches the user before `parse_request` has run, so a test on `$wp->query_vars['rest_route']` would silently never match. Three forms are matched: `/wp-json/…`, `/index.php/wp-json/…` and `?rest_route=…`.
- **`?rest_route=` only counts on the front controller** (request path equal to the home path or `/index.php`). The spike's first version tested the query variable alone: `admin-ajax.php?rest_route=/mcp/mcp-adapter-default-server` with the token ran the logged-in `wp_ajax_*` handlers as the token's user (reproduced on the bench with `heartbeat`), and `admin-post.php` or `wp-comments-post.php` would have done the same. Any audience check must test the script, not just the route.
- Without a user the Adapter already answers `401 rest_forbidden`, but **without** `WWW-Authenticate`: Claude ignores a `401` without the pointer, and ignores the header on any other status. `rest_post_dispatch` adds `Bearer resource_metadata="…", scope="mcp"` (plus `error="invalid_token"` for a wrong token) to every `401` of the MCP route only. `rest_post_dispatch` also fires for the errors returned by `rest_authentication_errors`.
- `/authorize` returns a REST response carrying `Location` rather than `wp_redirect()` + `exit`, so `rest_post_dispatch` stays in the loop.

## Discovery documents

Served from `parse_request` @0 and followed by `exit`, before `redirect_canonical` or the 404 handling. `$wp->request` is the path relative to the home URL. Both answer `200` JSON with `no-store` and `Access-Control-Allow-Origin: *`.

- `resource` equals the URL the user pastes, path included (`rest_url()` without trailing slash). `resource_metadata` uses the RFC 9728 path-insertion form, `/.well-known/oauth-protected-resource/wp-json/mcp/mcp-adapter-default-server`, which is the URL Claude Code actually fetched first; the bare `/.well-known/oauth-protected-resource` is served too (Claude probes it when the pointer is missing). A single entry in `authorization_servers`: Claude only reads the first.
- The issuer is `home_url()`, one authorization server per site: a token of site A means nothing to site B on the same VPS. Every URL comes from `home_url()` / `rest_url()`, never from the `Host` header.
- `client_id_metadata_document_supported: true` **and** `none` in `token_endpoint_auth_methods_supported` are both required for Claude to use CIMD; without either it falls back to DCR. `registration_endpoint` is absent unless DCR is on: Claude Code did not attempt DCR when CIMD is advertised.
- `offline_access` is listed in the authorization server's `scopes_supported` only, not in the protected resource document nor in the challenge: MCP 2026-07-28 says a resource SHOULD NOT list it; clients add it themselves when the authorization server advertises it. A refresh token is always issued anyway: a connection that cannot refresh would need a new consent every hour.
- With the module off or `LUMIA_DISABLE_MCP_CONNECT` set, the documents and every OAuth route answer `404` and the Bearer filter is not added.

## Consent screen

- **Hidden page** (empty parent, `''` and not `null`: `null` triggers deprecation notices in `plugin_basename()` on PHP 8.1+) with the `read` capability, so any signed-in user reaches it; the approver capability (`manage_options` by default, `edit_others_pages` in the settings, filter `lumia_mcp_connect_approver_capability`) is checked inside to show a clear refusal instead of WordPress's generic page. A filter returning nothing usable falls back to the setting: an empty capability would be harmless, a non-string would fatal in `current_user_can()`.
- A hidden page has no menu entry for `get_admin_page_title()`: the title is set on `load-`, otherwise `admin-header.php` passes `null` to `strip_tags()`.
- `X-Frame-Options: DENY`, `frame-ancestors 'none'` (clickjacking of the Approve button), `no-store`, and no `Referer` to the client's logo host (the URL carries the request id). These replace the `SAMEORIGIN` core sends on `admin_init`.
- `Admin::enqueue_assets()` only loads the design-system styles on screens whose hook contains `lumia-tools`, which this one does not: the page enqueues the same handles itself.
- The page shows the client name and logo, "Verified: Claude" or a warning for an unverified client, the **redirect host** in clear (with a note when the code goes to an application on the user's computer), the account the connection will act as, the scope in words, the site and the resource URL. An optional **label** ("Clement, MacBook") is stored with the connection and shown in the list and the Activity Log.
- The nonce is bound to the request (hash of its id) on top of the user: a nonce shown for one request cannot approve another.
- No URL of this flow goes through `wp-login.php`: the Security module's `site_url` filter re-parses such URLs and would mangle the redirect.
- **Loopback redirect → interstitial.** `https` callbacks get a plain `302` (`wp_redirect()`, not `wp_safe_redirect()`: the host is the client's and the URI was matched exactly). Loopback `http` callbacks (Claude Code) get a tiny page with a meta refresh and a link instead (see the CSP pitfall below). No inline script, so no `script-src` concern.

## Agent role and account

- Connections act as a dedicated account (`claude-mcp`, display name "Claude (MCP)", email `claude-mcp+<site host>@invalid.invalid` in the reserved `.invalid` domain (the host keeps it unique across a multisite network), id in the non-autoloaded option `lumia_mcp_agent_user_id`), not as the approver: what Claude does is attributed to it in the revisions and the Activity Log, and its permissions are locked down independently. "Act as me" is offered per connection, off by default, with a warning.
- The account cannot sign in with a password (`wp_authenticate_user`), nor with an application password, and never sees the dashboard (`admin_init`, AJAX and `admin-post.php` left alone). A real person who was also given the role keeps their sign-in: only the dedicated account or a user whose single role is the agent role is locked.
- **Presets**: two, both built from the **administrator role** (plus the editor role, the core content capabilities and `bricks_full_access`, so a renamed administrator role still leaves a working floor) rather than from a fixed list. **Administrator** is the default since 2.4.0 (issue #52) and adds `Agent::CODE_CAPS` (`unfiltered_html`, `unfiltered_upload`, `bricks_execute_code`, `bricks_full_access`) even when the administrator role lacks them. **Editor** drops `Agent::FORBIDDEN_CAPS` (site settings, users, plugins, themes, core updates, `unfiltered_html`/`unfiltered_upload`, file edits, import/export, `bricks_execute_code`, role editing `edit_roles`/`create_roles`/`delete_roles` (Members), `rank_math_edit_htaccess` and `rank_math_role_manager`, the legacy `level_8` to `level_10`) and every capability starting with one of `Agent::FORBIDDEN_PREFIXES` (`ure_`, User Role Editor), both through `Agent::is_forbidden()`; **Administrator** keeps everything. `read` is always kept: without it the Adapter's transport check refuses every call. Filter `lumia_mcp_connect_agent_capabilities` adjusts a preset; under Editor the forbidden capabilities are dropped after the filter, whatever it says.
- **Administrator by default, Editor by choice (2.4.0).** Tested on lumia-lp under Editor: Claude edited Bricks pages and Motion settings, but every JavaScript write was refused by the Bricks abilities (`bricks_code_sensitive_write_forbidden`: page scripts need `unfiltered_html`), SCF and the Bricks settings answered "permission denied" (`manage_options`), and the agency had to paste every GSAP animation into FluentSnippets by hand. The agency accepts the risk on its sites and revokes connections once the work is done. `Agent::current_preset()` reads, in order: the `LUMIA_MCP_AGENT_PRESET` constant (`admin` or `editor`; any other value is ignored), the stored setting, then the default. An unknown stored value (a 2.3.0 preset) reads as Administrator. A stored Editor is **migrated once** to Administrator: until 2.4.0 Editor was the default and was stored without anyone choosing it (the activation writes the module defaults with `add_option()`, and the form always posts the select), so keeping it would have left most sites, lumia-lp included, on Editor. The migration runs in `Agent::maybe_sync()` when the sync marker does not exist yet (the first request on 2.4.0 or later); Editor chosen after that stands. Connections approved under Editor gain the Administrator rights without a new consent: revoke them after the update if that matters. With the constant set, the select is disabled and absent from the form: `save_settings()` then keeps the stored choice instead of the default, so removing the constant brings it back. `save_settings()` resyncs the role to the *active* preset, not to the posted one, for the same reason.
- **Constants defined by the plugin (2.4.1, issue #59).** Sites are created from a seed that carries the database, while the hosting template (wp-dokploy-template) generates wp-config.php: `BRICKS_ENABLE_PHP_ABILITIES` and `ALLOW_UNFILTERED_UPLOADS` could not reach new sites. `Agent::define_code_constants()`, called at file load from lumia-tools.php right after `Discovery::boot()`, defines both (`true`) when MCP Connect is active (`Discovery::enabled()`, the raw autoloaded flag) and the active preset is Administrator, unless they are already defined. File load is before the theme, so before Bricks reads its constant; WordPress reads the upload one in `map_meta_cap()`. A value set in wp-config.php, `false` included, always wins; `Agent::constant_source()` tells the Help tab and Site Health which one applies. They apply to the whole site, not only to the Claude account: any administrator (any super admin on a network) may then upload any file type. **Not defined when wp-config.php forbids file changes or the code editors** (`DISALLOW_FILE_MODS`, `DISALLOW_FILE_EDIT`, independent review): `unfiltered_upload` skips the file-type check, so a `.php` file could land in `uploads/`, which is the code execution those constants are there to prevent. `constant_source()` returns `config` for a value set anywhere else (wp-config.php, a mu-plugin): the messages say "outside Lümia Tools". On the first request after an update from 2.3.x the stored Editor preset is only migrated at `init` (`Agent::maybe_sync()`), after file load: the constants appear from the next request.
- **What the constants still block under Administrator** (Site Health and Help tab, `SiteHealth::code_checks()`): `DISALLOW_UNFILTERED_HTML` and multisite (only super admins hold `unfiltered_html` there) turn JavaScript into `do_not_allow` in `map_meta_cap()`; `DISALLOW_FILE_MODS` blocks plugin installs and updates (read through `wp_is_file_mod_allowed()`); `unfiltered_upload` still needs `ALLOW_UNFILTERED_UPLOADS` (and is a super-admin right on a network); plugin installs, updates and deletions are super-admin rights on a network too; `bricks/execute-php` needs `BRICKS_ENABLE_PHP_ABILITIES` and its toggle in Bricks > AI (off by default in Bricks, not written by the module).
- **Resync without an admin visit**: `Agent::maybe_sync()` runs in `Module::init()` and compares the autoloaded option `lumia_mcp_agent_sync` (`<preset>|<plugin version>`) with the current one. Token requests never load an admin page, so before it a new default preset or a capability added by a release only reached the role on the next administrator visit, and a connected Claude kept the old rights until then. When the marker differs it writes the marker first (concurrent requests after an update then skip instead of each rewriting the role; `sync_role()` still drops and recreates the role, so a request reading the roles between the two writes can be refused once), then resyncs the role and resets the account. A `lumia_mcp_connect_agent_capabilities` filter added later than `init` is only applied by the next administrator page load.
- **Why the administrator role and not a list** (2.3.0 had three fixed lists: "Content and Bricks", "+ SEO", "Full shop"): tested on a client site, Claude connected but could edit nothing. Two causes. First, Bricks registers no ability until "Enable Bricks abilities" is on (see below), so changing the preset changed nothing visible. Second, once on, `bricks/list-nav-menus` asks for `edit_theme_options` and the Bricks settings, breakpoints and fonts for `manage_options`, which no list held, and each plugin (WooCommerce, Rank Math, a form plugin) has its own capability names. Every plugin grants its capabilities to administrators, so following that role covers any stack without a preset per plugin. The price: a capability a plugin hands administrators reaches Editor too, unless it is forbidden. Not every dangerous one goes through `manage_options`: Members and User Role Editor let a role editor give `manage_options` to any other role (escalation for every other account, the agent's own check only covers the agent), Rank Math's `.htaccess` editor becomes code execution on Apache. Those are listed; a new plugin with such a capability needs adding to the list, which the independent review of this change caught. Deliberately kept: `manage_woocommerce`, so Editor manages the shop (products, orders, coupons, and also the shop settings, payment gateways and webhooks): the agency wants Claude to work on any stack. On upgrade from 2.3.0 the existing connections get these rights without a new consent. A 2.3.0 preset still stored read as Editor until 2.4.0, as Administrator since (the default), and the role is resynced on the next request (`Agent::maybe_sync()`). `edit_theme_options` left `FORBIDDEN_CAPS` for the menus; the Customizer's additional CSS and HTML widgets still need `unfiltered_html`.
- **Editors rarely delegate now**: `Agent::can_delegate()` lets a non-administrator approver hand a connection to the dedicated account only when they hold every capability of the preset, and an editor never holds an administrator's. With the approver setting on `edit_others_pages`, editors connect Claude as themselves.
- **The role is rebuilt from the preset whenever it drifts**: `Module::maybe_ensure_agent()` calls `Agent::sync_role()` on every non-AJAX admin load of an administrator (two arrays compared, nothing written when they match), as do activation, a preset change and an agent-mode approval. A capability added by hand, by a role editor or by another plugin does not survive the next admin load. When it changed, the role is dropped and recreated (two option writes) rather than updated cap by cap. The first version only repaired a missing role or account, so the documented resync never ran and a `manage_options` written on the role stayed there. The same admin load runs `Agent::reset_account()`: the role resync does not see drift on the **account** itself, so a second role (`administrator`, `shop_manager`) or a capability granted to the user is removed there. `FORBIDDEN_CAPS` include the multisite `manage_network*` family, since Files and Database require `manage_network_options` on a network.
- **`FORBIDDEN_CAPS` are also denied at check time**: `Agent::deny_forbidden_caps()` on `user_has_cap` @999 sets them to false for a locked agent (the dedicated account, or a user whose single role is the agent role), so a capability written on the role, or directly on the account, between two admin loads never takes effect for a token request (which never loads an admin page). Only the forbidden list: other drift waits for the next resync.
- **Bricks builder access**: Bricks grants it through its own role settings, which write `bricks_full_access` / `bricks_edit_content` on the role and may remove them when those settings are saved. The resync puts the preset back on the next admin load: the presets carry `bricks_full_access`, so builder access cannot be removed from the agent through Bricks' settings (use the `lumia_mcp_connect_agent_capabilities` filter), and `bricks_execute_code` granted there is dropped (and denied meanwhile). `Agent::bricks_status()` still checks the **role**, not the preset, and the Help tab and Site Health warn when the role has no builder access on a Bricks site (a filtered preset without it, or a Bricks save not yet resynced).
- **Bricks abilities**: Bricks 2.4 registers its ~170 abilities (pages, elements, templates, classes, variables, menus, forms, media) only when "Enable Bricks abilities" is on in Bricks > AI, global setting `abilitiesApi` in the `bricks_global_settings` option, off by default. Off, the Adapter lists the three core read-only abilities and nothing to edit, which looks like a permission problem and is not. `Module::on_activate()` turns it on (`Agent::enable_bricks_abilities()`), only there so an explicit choice to turn it off later stands: a site where the module was already active before 2.3.1 only gets the warning, and deactivating or uninstalling the module leaves the setting on. Before Bricks 2.4 the setting does not exist: the status reads `unsupported` and nothing is written; `Agent::bricks_abilities_status()` feeds a Help tab and Site Health warning. Bricks' own step 2 there (an application password) is not needed: the OAuth connection sees the abilities as soon as they are on, without reconnecting. `bricks/execute-php` stays out of reach under Editor (`bricks_execute_code` is forbidden).
- Account deleted by hand: its option is cleared and the next administrator visit recreates it; the connections acting as, or approved by, any deleted user are revoked. An existing account carrying the role is adopted when the option is lost (database import).
- Uninstall (`Module::uninstall_data()`, called by `uninstall.php` before the keys are deleted since it reads the option) deletes the account, its content going to the administrator with the lowest id so pages Claude wrote survive, then the role.

## Abilities for Claude (`lumia/*`)

`McpConnect\Abilities\` (issue #53). Through MCP, Claude only had the Bricks abilities and three core read-only ones: it could not read the error log after a change, check the rendered page, purge a cache, manage plugins, write a FluentSnippets snippet or the Rank Math SEO of a page. These abilities fill that gap. They live in MCP Connect rather than in a module of their own: they are useless without it, and every site that runs MCP Connect gets them without a second switch.

- **Registration** (`Registry::boot()`, called from `Module::init()`, even when the protocol is off: an application password reaches them through the Adapter too). The Abilities API (WordPress 6.9+) builds its registry lazily, on first use, firing `wp_abilities_api_categories_init` then `wp_abilities_api_init`: the hooks are added, or, when another plugin already built the registry during `init`, the abilities go straight into `WP_Abilities_Registry` / `WP_Ability_Categories_Registry` (`wp_register_ability()` and `wp_register_ability_category()` refuse anything outside their action). Category `lumia-tools`, names `lumia/<name>`, `meta.mcp.public` true so the Adapter's default server lists them, annotations `readonly` / `destructive` / `idempotent` set per ability. Descriptions are written for Claude, in English, and not translated (they are not UI); labels are.
- **Families** (`Abilities\Family`), each turned on or off under Settings > Tools for Claude (`abilities` setting, every family on by default, one checkbox each, rebuilt from the whitelist in `save_settings()`; the form posts a hidden `abilities[_sent]`, and a payload without it, such as a configuration exported before 2.4.0, keeps the stored families instead of turning them all off):
  - `Diagnostics`: `get-environment` (versions, active plugins, PHP limits, constants, caches, cron), `read-error-log` (the end of `WP_DEBUG_LOG` or of the PHP `error_log`, at most 2 MB read and 2000 lines returned, filters `contains` and `since`; a line without a `[date]` prefix follows its entry), `clear-error-log` (truncates, never deletes: the server may hold the file open).
  - `HttpProbe`: `http-request`, GET or HEAD on a URL of the site only (scheme http(s), host and port of `home_url()` or `site_url()`, no user info; a path is resolved against the home URL; a protocol-relative `//host` is refused). Redirections are followed by hand, at most 5, and one to another host is reported, never followed. Through `wp_safe_remote_request()`, which lets the site's own host through even on a private address (container network) and refuses ports other than 80, 443 and 8080 (`http_allowed_safe_ports`). Cache bypass by a `lumia_nocache` query argument plus `Cache-Control: no-cache`. `as_agent` sends a logged-in cookie of the Claude account, built from a session token created for the request and destroyed after it (`WP_Session_Tokens`). Formats: `summary`, `seo` (title, description, canonical, robots, headings, Open Graph and Twitter, JSON-LD, hreflang, images without alt, link counts: `HttpProbe::extract()`, DOMDocument) and `html` (truncated). `Set-Cookie` values are masked.
  - `Cache`: `purge-cache` (page cache through the public hooks or functions of Cache Enabler, WP Rocket, LiteSpeed, W3 Total Cache, WP Super Cache, WP Fastest Cache, SiteGround, Breeze, Nginx Helper; object cache; OPcache, reported false when `opcache.restrict_api` refuses; expired transients). The Bricks CSS files stay with `bricks/regenerate-css-files`.
  - `Plugins`: `list-plugins`, `install-plugin` (wordpress.org slug or https zip URL), `update-plugin`, `activate-plugin`, `deactivate-plugin`, `delete-plugin`. **Lümia Tools and the plugin that loaded the MCP Adapter's class are never deactivated nor deleted** (`Plugins::is_protected()`): Claude would cut its own connection mid-task. Updating them is allowed. Outside cron, `Plugin_Upgrader::upgrade()` deactivates the plugin silently before the copy and leaves the reactivation to the browser of the update screen: the ability puts it back in `active_plugins` the same silent way, in a `finally` so a failed copy (rolled back by WordPress, still deactivated) does not leave Lümia Tools or the Adapter off, because `activate_plugin()` would include a main file this request may already have loaded. The upgrader needs direct file access (`get_filesystem_method()` = `direct`): an FTP prompt cannot be answered through MCP.
  - `Options`: `get-option` (or a name search), `update-option` (replace, or `merge` an array into the stored one), `delete-option`. Writes are refused for `siteurl`, `home`, `active_plugins`, `template`, `stylesheet`, `cron`, the salts, `default_role` and `users_can_register` (anyone registering would become an administrator), the roles option (`<prefix>user_roles`) and every `lumia_` / `skmt_` / transient option: the Lümia Tools settings go through their screens, which sanitize them. **Collation pitfall** (independent review): `option_name` is compared by MySQL with a case- and accent-insensitive collation, so `sitéurl` matched the `siteurl` row and passed a PHP comparison; names are now limited to `[A-Za-z0-9_-.:]` and the deny list is checked on the name as stored. Reads have no deny list: under the Administrator preset Claude can read anything an administrator can.
  - `Snippets` (when FluentSnippets is active): `list-snippets`, `get-snippet`, `create-snippet`, `update-snippet`, `delete-snippet`. Through FluentSnippets' own `Helper::createSnippet()` / `Helper::updateSnippet()` and `Snippet` model, then its actions (`snippet_created`, `snippet_updated`, `snippet_status_updated`, `snippet_deleted`), so its index and cache follow and its checks apply: invalid PHP, or PHP starting with `<?php`, is refused before anything is written (FluentSnippets lints the code and runs it once). Its REST authoring switch (off by default, `FLUENT_SNIPPETS_REST_AUTHORING`) is not involved. `createSnippet()` forces a draft (or follows its auto-publish setting): a published status is applied afterwards the way its status endpoint does. FluentSnippets' error details (title with the line, reason, fix) become the message Claude reads. A PHP snippet is stored with its opening `<?php` and refused when sent back with it: the code Claude reads and resends is the editable one (the tag dropped, as FluentSnippets' own `editableCode()` does), and only the status change writes the raw stored code back through the model.
  - `Seo` (when Rank Math is active): Rank Math 1.0.28x already registers `rank-math/*` abilities that read a post's SEO (rendered), the redirections, the 404 log and the settings, and write the global settings, but none writes the SEO of one post nor a redirection. `seo-get-post` / `seo-update-post` read and write the raw `rank_math_*` post meta (with their %variables%; an empty value deletes the field so the post type default applies; `pillar_content` stored as `on` or nothing, `twitter_use_facebook` as `on` / `off`, as Rank Math does). `seo-save-redirection` / `seo-delete-redirection` go through `RankMath\Redirections\Redirection::from()->save()` and `DB::delete()`, only when the redirections module is on (its table exists then); a destination equal to an exact source is refused (`is_infinite_loop()`).
- **Permissions**: each ability checks one capability (`manage_options` for most, `activate_plugins` / `install_plugins` / `update_plugins` / `delete_plugins` for plugins, `edit_posts` then `edit_post` for the SEO of a post). Under the Editor preset most of them are refused, which is the point of that preset.
- **Activity Log**: every ability that is not read-only fires `lumia_mcp_ability_executed` with its name and its short scalar arguments (`Registry::log()`; `code`, `value`, `content` and `zip_url`, which may carry a signed token, are left out; no role exclusion, like every MCP event); the Activity Log writes `mcp_ability_executed` ("Claude action", group `mcp`). Plugin activations, option changes and post meta are also logged by their own core hooks.
- **Static analysis**: FluentSnippets, Rank Math and the MCP Adapter are not in the repository; `tools/phpstan-abilities.stub` declares what the abilities call, with the signatures read in FluentSnippets 10.58 and Rank Math 1.0.280. A method of those plugins is assumed present once its class exists.

## Admin screen

Three tabs in the module form:

- **Connections** (default): status line (active or paused), table loaded by AJAX (`lumia_mcp_connect_list`): label, client with its verified badge, acts as, approved by, created, last used, last IP, refresh expiry, status; **Revoke** per row and **Revoke all**, both behind a confirmation modal. The `client_id`, scope and token data never leave the server; a DCR client is never shown as verified, whatever its name.
- **Settings**: the families of `lumia/*` abilities (Tools for Claude), pause all connections (every Bearer answers `401`, `/authorize` and `/token` refuse, data kept), approver capability, role preset (locked when `LUMIA_MCP_AGENT_PRESET` is set), trusted publishers only, DCR and its purge delay, token lifetimes (access 5 to 1440 minutes, refresh 1 to 365 days). The state of `LUMIA_DISABLE_MCP_CONNECT` is shown, as Security does for its constant. Every key is rebuilt from a whitelist in `save_settings()`: the option is diffed into the Activity Log on every write, so nothing volatile goes there.
- **Help**: the URL to paste with a copy button, the four steps in Claude, the Claude Code command (`claude mcp add --transport http <name> <url>`, then `/mcp` to sign in), and the environment checks shared with Site Health.

Deactivating the module keeps data, role and account: every connection stops (the routes disappear) and resumes on reactivation.

## Activity Log

`Connections` documents five actions, listened to by the Activity Log (group `mcp`, see [activity-log.md](activity-log.md)): `lumia_mcp_connect_authorized` (code exchanged), `_denied`, `_revoked` (reason `manual`, `all`, `reuse`, `user_deleted`, `token`, `expired`), `_refresh_reuse` and `_client_registered`. After a successful Bearer authentication, `BearerAuth` adds a `lumia_activity_log_record` filter for the rest of the request that sets `details.via = 'mcp'`, the connection label (or client name) and its id: every content, media, option or Bricks change made through Claude says which connection made it. Never the token. The filter is only added after a success, so it costs nothing elsewhere and needs no guard when the Activity Log is off.

## Site Health

Registered under `is_admin()` only. `direct` tests, each loopback with a 5 s timeout and no redirect followed (an http → https or login redirect is itself the problem to report):

- **Discovery**: both documents `200` JSON, naming this site, in `https`. The failure text gives the nginx rule below.
- **Authorization header**: `POST /ping` with `Authorization: Bearer lmc_probe`; the route reports whether the header reached PHP through the same reader as the Bearer check, and never authenticates. The failure text gives the Apache, LiteSpeed and nginx rules.
- **Environment**: MCP Adapter active and at least 0.7, pretty permalinks, `https` home URL, agent account present, permission preset, Bricks abilities, Bricks builder access.

With `LUMIA_DISABLE_MCP_CONNECT` the two protocol tests are not registered: they would report the `404` the constant asks for.

## Hosting pitfalls

- **nginx of `wp-dokploy-template` blocks `/.well-known/`.** Its `location ~ /\\. { deny all; }` (hidden files) answers `403` to every `/.well-known/*` before PHP (checked on boilerplate.agence-lumia.com: `security.txt`, `acme-challenge` and the OAuth paths all `403`). The template needs `location ^~ /.well-known/oauth- { try_files $uri /index.php?$args; }` (a `^~` prefix location wins over every regex location, wherever it is written), as was done for `robots.txt`; proposed upstream in agence-lumia/wp-dokploy-template#5. Until a site runs the fixed template, add it to `nginx-security.conf`, the per-site file of the webroot that `default.conf` includes inside the main `server` block: `default.conf` itself is a read-only bind mount rewritten by Dokploy on each deploy. The Site Health discovery test detects the `403`.
- **`Authorization` header.** nginx passes it to PHP-FPM (`HTTP_AUTHORIZATION`). Apache only does through the rewrite rule WordPress writes in `.htaccess` (`E=HTTP_AUTHORIZATION:%{HTTP:Authorization}`, read back as `REDIRECT_HTTP_AUTHORIZATION`); under mod_php `getallheaders()` still has it. `BearerAuth::authorization_header()` reads all three. Without the header every token is invisible and Claude loops on the sign-in. Checked on boilerplate: the header reaches PHP-FPM through Traefik and nginx, and `home_url()` / `rest_url()` are `https` behind the proxy.
- **CSP `form-action` and the loopback callback.** The template sends `X-Frame-Options: SAMEORIGIN` and a CSP with `frame-ancestors 'self'` and `form-action 'self' https:` on every response. Chromium applies `form-action` to the redirect that follows a form submission too, so a `302` from the consent `POST` to Claude Code's `http://localhost:<port>/callback` would be blocked: hence the interstitial page, whose meta refresh is a navigation started by the page, not subject to `form-action`. The consent page's own `DENY` / `'none'` must be checked against the merged headers (nginx adds its own on top of PHP's).
- **Cache Enabler cannot cache the OAuth responses** (1.8.17, read in `cache_enabler_engine.class.php`): it only stores a response containing `<html` and an HTML doctype, and skips REST requests, non-`GET` methods, non-`200` statuses, an `Accept` without `text/html` and `DONOTCACHEPAGE`. The explicit exclusions planned in the issue were therefore unnecessary; `DONOTCACHEPAGE` and `Cache-Control: no-store` stay on every discovery, authorize, consent, token and revoke response as a belt for other page caches. The nginx static bypass of the template only serves files Cache Enabler wrote, so it cannot either.
- **Redis object cache.** Nothing security-relevant lives in the object cache: codes, refresh tokens and requests are consumed with the atomic `UPDATE` above. Only the CIMD negative cache, the fetch budget and the DCR counter are transients, where an approximate count is fine.
- **Application passwords need HTTPS** (or `WP_ENVIRONMENT_TYPE=local`): on the plain-HTTP bench they are disabled and a `Basic` header is silently ignored. Behind Traefik they are available (`is_ssl()` is true there).
- **Claude Code remembers "needs authentication" per server name.** After a call without a token, adding the `Authorization` header to the same server entry was not enough: it kept reporting the server as unauthorized until the entry was renamed. When testing, or when a teammate switches from an application password to OAuth or back, use a new server name or clear the authentication with `/mcp`.
- Anthropic's inbound traffic comes from `160.79.104.0/21` if a firewall rule is ever needed. All sites of a VPS share its outbound IP for CIMD fetches: the per-site budget is enough.

## Known limits

- **Pretty permalinks required.** `$wp->request` is only filled when rewrite rules exist; with plain permalinks the documents are never served and the MCP URL itself is `/index.php?rest_route=…`. Our sites all use `/%postname%/`; Site Health and the Help tab flag the other case as critical.
- **Subdirectory installs** (`https://x.com/site`): RFC 9728 and RFC 8414 put `/.well-known/…` at the **origin root**, which a WordPress installed under `/site` never receives. `resource_metadata` therefore points under the home URL (any URL is valid there; identical to the RFC form on a root install). The authorization server document has no such escape: the client derives its URL from the issuer, so a subdirectory install needs a server-level rewrite of `/.well-known/oauth-authorization-server/site` to WordPress. Out of scope for our root-installed sites.
- **An mu-plugin resolving the user while loading still wins**: it runs before `lumia-tools.php` is loaded, so the first `wp_get_current_user()` caches an anonymous user and every MCP call answers `401`. Nothing a regular plugin can do about it.
- **`WP_PROXY_HOST` weakens the pinning.** Through an outbound proxy, cURL connects to the proxy and the proxy resolves the CIMD host itself: `CURLOPT_RESOLVE` no longer decides the address, and the resolution check only covers what the site saw. The other guards (URL shape, trusted publishers, budget, size and time limits) still apply.
- **Turning "Trusted publishers only" back on does not cut existing DCR connections.** It is checked at `/authorize` and at the consent, not at `/token` nor on the Bearer: connections approved while it was off keep refreshing. Revoke them by hand.
- **Owner / Team sharing not verified**: whether a connector added by an organization Owner in a Team plan is shared with members, each member authorizing individually, is not documented and was not tested.
- Abilities that check `manage_options` (the Bricks settings, breakpoints and fonts, the SCF field group and post type abilities, `core/get-site-info`, the `lumia/*` abilities) only work under the Administrator preset, the default.
- **Approval prompts in Claude**: each `mcp-adapter-execute-ability` call asks for approval in the Claude apps. That is the client's per-tool setting (connector settings, set the tool to always allow), not something the site can turn off.

## How to test

`tools/e2e/mcp-connect/run.sh` (see [its README](../../tools/e2e/mcp-connect/README.md)) runs the whole campaign against the Docker bench: discovery, the full OAuth flow with Claude Code's real client metadata document (the container must reach `claude.ai`), token audience, refresh rotation and reuse detection, code replay, `/authorize` errors and SSRF guards, revocation, pause and constant, the agent account, the Activity Log, consent refusal and the admin screens; `--uninstall` adds the cleanup checks. Its pitfalls (nonces need a stable session, OPcache caching `wp-config.php`, Git Bash path conversion, loopback Site Health tests failing on plain HTTP) are in that README.

End to end with a real client: `claude mcp add --transport http <name> https://<site>/wp-json/mcp/mcp-adapter-default-server`, then `/mcp` to sign in; for the hosted apps, add the same URL as a custom connector. The spike (removed since) was checked this way on the bench (WordPress 7.1.3, Apache, MCP Adapter 0.7.1) and on boilerplate.agence-lumia.com (Dokploy, Traefik, nginx, PHP-FPM, Cache Enabler and Redis active), where Claude Code with the Bearer header listed the site's 51 abilities.
