# MCP Connect module

`includes/Modules/McpConnect/`. OAuth 2.1 sign-in so that each site can be added to Claude as a custom connector (issue #46). **Status: spike only** (`Spike.php`, task 1): it proves the hook-in point on MCP Adapter 0.7.1 and is not a module yet (no definition, no screen, no table).

## Spike (`Spike.php`)

Loaded from `lumia-tools.php` at file load (see below why not on `plugins_loaded`), only when `wp-config.php` defines `LUMIA_MCP_SPIKE_TOKEN` (prefix `lmc_at_` + 32 characters or more) **and** `LUMIA_MCP_SPIKE_USER` (an existing login). Without both, nothing is hooked. The token acts as that user on the MCP route; the `/authorize` endpoint only records what the client sent (option `lumia_mcp_spike_authorize_log`, last 20 requests) and never issues a code; `/token` and `/revoke` answer `invalid_grant`.

Checked on the Docker bench (WordPress 7.1.3, Apache, MCP Adapter 0.7.1): missing or invalid token → `401` with the challenge; valid token → `initialize` and `tools/list` work; the same token on `/wp/v2/users/me` or `/wp/v2/settings` stays anonymous; the `?rest_route=` form behaves the same; application passwords keep working side by side; both discovery documents answer `200` JSON `no-store`. Claude Code 2.1.310 without a header follows the whole discovery chain (`POST` MCP → `401` → `/.well-known/oauth-protected-resource/wp-json/mcp/mcp-adapter-default-server` → `/.well-known/oauth-authorization-server`) then asks for the interactive sign-in; with the header it lists and calls the abilities.

Also checked on boilerplate.agence-lumia.com (Dokploy, Traefik, nginx, PHP-FPM, Lümia 2.2.4 + the spike files, Cache Enabler and Redis active), once `/.well-known/oauth-` was let through nginx (below): the same checks pass with `https` URLs everywhere, which proves that the `Authorization` header reaches PHP-FPM through Traefik and nginx and that `home_url()` / `rest_url()` are `https` behind the proxy; Claude Code with the Bearer header lists the 51 abilities of the site.

## Hook-in on the MCP Adapter

- The Adapter never reads the `Authorization` header itself. Its transport `permission_callback` is `current_user_can( 'read' )` (filter `mcp_adapter_default_transport_permission_user_capability`) when no custom callback is given, so authenticating a user on `determine_current_user` is enough. Its sessions (`Mcp-Session-Id`) live in that user's meta: they work unchanged for a Bearer user.
- The Adapter creates its servers on `rest_api_init` @15 and registers the route @16. The authentication hooks do not depend on that order: `determine_current_user` runs whenever the current user is first needed, `rest_authentication_errors` and `rest_post_dispatch` around the dispatch.
- **The filter is added at file load, not on `plugins_loaded`.** `_wp_get_current_user()` caches its first result for the whole request, an anonymous `WP_User( 0 )` included: a plugin resolving the user on `plugins_loaded` before Lümia's callback (priority below 10, or same priority and a folder sorting before `lumia-tools/`) locked every MCP call to `401` whatever the token. Core's cookie and application-password handlers have no such problem because `default-filters.php` adds them before any plugin loads. An mu-plugin that resolves the user while loading still wins: nothing a regular plugin can do about it. Checked on the bench with a plugin resolving the user on `plugins_loaded` @1.
- **Route detection reads the raw request URI**, not the parsed REST route. Any plugin calling `wp_get_current_user()` on `init` (or earlier) resolves and caches the user before `parse_request` has run, so a test on `$wp->query_vars['rest_route']` would silently never match. Three forms are matched: `/wp-json/…`, `/index.php/wp-json/…` and `?rest_route=…`.
- **`?rest_route=` only counts on the front controller** (request path equal to the home path or `/index.php`). The first version tested the query variable alone: `admin-ajax.php?rest_route=/mcp/mcp-adapter-default-server` with the token ran the logged-in `wp_ajax_*` handlers as the token's user (reproduced on the bench with `heartbeat`), and `admin-post.php` or `wp-comments-post.php` would have done the same. Any audience check of the module must test the script, not just the route.
- `determine_current_user` @30: after the core cookie and application-password handlers, so a request they authenticated is left untouched; the Bearer is only considered when no user was found.
- Without a user the Adapter already answers `401 rest_forbidden`, but **without** `WWW-Authenticate`: Claude ignores a `401` without the pointer. `rest_post_dispatch` adds `Bearer resource_metadata="…", scope="…"` (plus `error="invalid_token"` for a wrong token) to every `401` of the MCP route only. `rest_post_dispatch` also fires for the errors returned by `rest_authentication_errors`.
- A wrong Bearer token is answered `401 invalid_token` from `rest_authentication_errors` rather than falling back to an anonymous request.

## Discovery documents

Served from `parse_request` @0 and followed by `exit`, before `redirect_canonical` or the 404 handling. `$wp->request` is the path relative to the home URL.

- `resource` equals the URL the user pastes, path included (`rest_url()` without trailing slash). `resource_metadata` uses the RFC 9728 path-insertion form, `/.well-known/oauth-protected-resource/wp-json/mcp/mcp-adapter-default-server`, which is the URL Claude Code actually fetched first.
- The issuer is `home_url()`; the authorization server metadata is at `/.well-known/oauth-authorization-server` (path-insertion form when the home URL carries a path).
- `registration_endpoint` is absent: Claude Code did not attempt Dynamic Client Registration when `client_id_metadata_document_supported` is `true`.
- `offline_access` is listed in the authorization server's `scopes_supported` only, not in the protected resource document nor in the challenge: MCP 2026-07-28 says a resource SHOULD NOT list it (refresh tokens are not a resource requirement); clients add it themselves when the authorization server advertises it.
- **Pretty permalinks required.** `$wp->request` is only filled when rewrite rules exist; with plain permalinks the documents are never served and the MCP URL itself is `/index.php?rest_route=…`. Our sites all use `/%postname%/`; the module's Site Health test must flag the other case.
- **Home URL with a path** (`https://x.com/site`): RFC 9728 and RFC 8414 put `/.well-known/…` at the **origin root**, which a WordPress installed under `/site` never receives. The spike therefore points `resource_metadata` under the home URL (any URL is valid there; identical to the RFC form on a root install). The authorization server document has no such escape: the client derives its URL from the issuer, so a subdirectory install needs a server-level rewrite of `/.well-known/oauth-authorization-server/site` to WordPress. Out of scope for our root-installed sites, to state in the module's help.

## Hosting pitfalls found by the spike

- **nginx of `wp-dokploy-template` blocks `/.well-known/`.** Its `location ~ /\\. { deny all; }` (hidden files) answers `403` to every `/.well-known/*` before PHP (checked on boilerplate.agence-lumia.com: `security.txt`, `acme-challenge` and the OAuth paths all `403`). The template needs `location ^~ /.well-known/oauth- { try_files $uri /index.php?$args; }` (a `^~` prefix location wins over every regex location, wherever it is written), as was done for `robots.txt`. On boilerplate it was added to `nginx-security.conf`, the per-site file of the webroot that `default.conf` includes inside the main `server` block: `default.conf` itself is a read-only bind mount rewritten by Dokploy on each deploy. The Site Health test of the module must detect the `403`.
- **Cache Enabler cannot cache the OAuth responses** (1.8.17, read in `cache_enabler_engine.class.php`): it only stores a response containing `<html` and an HTML doctype, and skips REST requests, non-`GET` methods, non-`200` statuses, an `Accept` without `text/html` and `DONOTCACHEPAGE`. The explicit exclusions planned in the issue are therefore unnecessary; `DONOTCACHEPAGE` and `Cache-Control: no-store` stay as a belt for other page caches. The nginx static bypass of the template only serves files Cache Enabler wrote, so it cannot either.
- **`Authorization` header.** nginx passes it to PHP-FPM (`HTTP_AUTHORIZATION`). Apache only does through the rewrite rule WordPress writes in `.htaccess` (`E=HTTP_AUTHORIZATION:%{HTTP:Authorization}`); under mod_php `getallheaders()` still has it. The spike reads all three.
- **Application passwords need HTTPS** (or `WP_ENVIRONMENT_TYPE=local`): on the plain-HTTP bench they are disabled and a `Basic` header is silently ignored. Behind Traefik they are available (boilerplate lists them in the REST index), so `is_ssl()` is true there.
- **Security headers set by nginx.** The template sends `X-Frame-Options: SAMEORIGIN` and a CSP with `frame-ancestors 'self'` and `form-action 'self' https:` on every response. For the consent page (task 5): the stricter `DENY` / `'none'` must be checked against the merged headers, and `form-action` also applies to the redirect that follows a form submission in Chromium browsers, so a `302` from the consent `POST` to Claude Code's `http://localhost:<port>/callback` may be blocked. Prefer a `GET` navigation to the callback after the `POST`, or test that redirect first.
- **Claude Code remembers "needs authentication" per server name.** After a call without a token, adding the `Authorization` header to the same server entry was not enough: it kept reporting the server as unauthorized until the entry was renamed. When testing, or when a teammate switches from the header to OAuth or back, use a new server name or clear the authentication with `/mcp`.
- **Object cache.** Boilerplate runs Redis Object Cache: confirms that codes and tokens must be consumed with an atomic `UPDATE` in the table, never through transients.
