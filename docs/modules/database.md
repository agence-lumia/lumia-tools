# Module Database

`includes/Modules/Database/Module.php` + `assets/admin/js/modules/database.js`. Explorateur/éditeur de tables au-dessus de `$wpdb`. `Module.php` est une fine couche AJAX (pas de réglages — `get_settings()`/`save_settings()`/`get_defaults()` sont des no-ops) ; toute l'interface est construite côté client depuis un gabarit à deux volets (`settings-template.php` : liste des tables en barre latérale + onglets Données/Structure/Requête SQL). Capacité requise : `manage_network_options` sous multisite (voir [core.md](../core.md#capacité-requise)).

Actions AJAX : `lumia_db_get_tables`, `lumia_db_get_rows`, `lumia_db_get_structure`, `lumia_db_update_row`, `lumia_db_delete_row`, `lumia_db_insert_row`, `lumia_db_truncate`, `lumia_db_drop_table`, `lumia_db_export_sql`, `lumia_db_run_query`, et pour le nettoyage `lumia_db_cleanup_scan`, `lumia_db_cleanup_run`, `lumia_db_cleanup_optimize`.

## Modèle de sécurité

Tout côté serveur, jamais de confiance au client.

- **Noms de tables/colonnes** : passent par `read_table()` → `validate_table()` (vérification contre `information_schema.tables` pour la base courante) et sont filtrés contre `get_columns_map()` (`SHOW COLUMNS`). Utilise `sanitize_text_field` (PAS `sanitize_key`) pour que les identifiants en casse mixte survivent.
- **Typage** : `column_format()` associe chaque colonne à `%d`/`%f`/`%s` pour `$wpdb->update`/`insert`/`delete` ; NULL est explicite (drapeau `set_null` / valeur null), rejeté côté serveur si la colonne est `NOT NULL`.
- **Éditeur SQL libre** (`ajax_run_query`). Tous les garde-fous testent la requête **normalisée** par `normalize_sql()`, jamais la chaîne brute ; c'est bien l'originale qui est exécutée ensuite.
  - `normalize_sql()` fait trois passes, et **l'ordre est le fond du sujet** : neutraliser les littéraux (`'…'`, `"…"`, `` `…` ``) d'abord — une ouverture de commentaire dans une chaîne n'ouvre rien, la traiter comme telle tronquerait la requête normalisée et masquerait la suite ; puis retirer les commentaires (`/* */`, `--`, `#`) ; puis compacter les espaces. Le trou exploité par l'audit était là : MySQL accepte un commentaire vide comme séparateur de mots, si bien qu'un `DROP` suivi d'un commentaire vide puis de `DATABASE` ne ressemblait à aucun mot-clé interdit tout en s'exécutant comme `DROP DATABASE`. **Étendre la liste noire n'y change rien** — il y a une infinité de façons d'écrire l'espace.
  - `find_forbidden_keyword()` compare des **mots entiers** (« migrant » ne contient plus « GRANT »). `FORBIDDEN_KEYWORDS` couvre aussi les accès disque du serveur MySQL : `INTO OUTFILE`, `INTO DUMPFILE`, `LOAD DATA`, `LOAD_FILE`.
  - `is_read_query()` ne se fonde **pas** sur le premier mot : un `SELECT` peut écrire (`INTO OUTFILE`), un `WITH … DELETE` s'ouvre sur un mot de lecture, et `SELECT 1; DELETE …` cache une seconde instruction. Il faut donc les trois : mot d'ouverture de lecture, aucun verbe d'écriture ailleurs, aucun point-virgule interne. Le sens de l'erreur est assumé — classer une lecture en écriture coûte une confirmation de plus, l'inverse coûte une table. `CREATE`/`DROP` sont volontairement hors de la liste des verbes d'écriture, pour que `SHOW CREATE TABLE` reste une lecture.
  - Toute écriture exige `$_POST['confirm']` (`database.js` pré-confirme via `window.lumiaModal` et **miroite** `normalize_sql()`/`is_read_query()` — sinon l'interface croit la requête inoffensive et le serveur répond `needs_confirm`) ; sans lui, retour `needs_confirm`.
  - Le plafond `QUERY_ROW_CAP` (1000) ne s'applique qu'aux requêtes ouvertes par `SELECT` ou `WITH` : `SHOW`, `DESCRIBE` et `EXPLAIN` rendent un jeu déjà fini et **n'acceptent pas de `LIMIT`** — l'ajouter transformait `SHOW CREATE TABLE x` en erreur de syntaxe. La présence d'un `LIMIT` se lit sur la forme normalisée, sinon un `/* LIMIT 1 */` en commentaire faisait sauter le plafond.
- `friendly_db_error()` traduit les erreurs MySQL courantes (entrée dupliquée, contrainte FK, NOT NULL, valeur incorrecte) en messages lisibles.
- **Export** (`ajax_export_sql`) : émission des valeurs selon le type (numériques sans guillemets, hex `0x…` pour le binaire, `NULL`, liste de colonnes explicite, `SET NAMES utf8mb4`). Les chaînes passent par `$wpdb->remove_placeholder_escape( esc_sql( … ) )` : depuis WP 4.8.3, `esc_sql()` remplace chaque `%` par un jeton de hachage que seul `$wpdb->prepare()` retire. Hors `prepare()`, le jeton restait dans le dump, et une valeur `50% off` ressortait en `50{64 caractères hexa} off` à la réimportation (corrigé à l'issue #50).

## Interface

Les onglets Données / Structure / Requête SQL utilisent le composant partagé `lumia-tabs` (voir [design-system.md](../design-system.md#onglets)) : `admin.js` gère l'affichage, et `database.js` ne fait que charger la vue ouverte sur l'événement `lumia:tab`, en l'ignorant tant qu'aucune table n'est choisie (au chargement, l'onglet mémorisé est restauré avant toute sélection). `switchTab()` passe par `window.lumiaTabs.activate()`, qui émet l'événement même si l'onglet est déjà ouvert : changer de table recharge donc bien les données. Chaque panneau garde `.lumia-db__tab-content`, dont le `display:flex` est neutralisé par `.lumia-tabs__panel[hidden]`, plus spécifique.

La hauteur de la mise en page est en CSS pur via la chaîne flex `.lumia-admin-main:has(.lumia-db)` (pas de handler de redimensionnement JS). L'historique SQL est local au navigateur (`localStorage`, avec un bouton d'effacement) — pas persisté côté serveur. Toutes les chaînes JS visibles passent par `lumiaAdmin.i18n` (alimenté par `get_admin_js_data()`). Pas d'édition dans l'onglet Structure, pas d'export CSV.

## Nettoyage

Remplace WP-Sweep (issue #16). Logique dans `Cleanup.php`, ouverte par l'entrée « Nettoyage » en tête de la barre latérale (vue globale, hors table sélectionnée). Endpoints dédiés et typés : l'élément à purger est une clé de `Cleanup::items()`, jamais du SQL, et rien ne passe par `ajax_run_query`. Portée : le site courant (`$wpdb->prefix`).

- **Par lots.** `lumia_db_cleanup_run` purge au plus `Cleanup::BATCH` (200) objets et renvoie `deleted` + `remaining` ; le JS rappelle tant que les deux sont non nuls. Un lot à `deleted = 0` arrête l'élément : sans ça, un objet que WordPress refuse de supprimer faisait boucler indéfiniment. `OPTIMIZE TABLE` suit la même logique, un appel par table, car il reconstruit une table InnoDB entière.
- **API WordPress quand l'objet en a une** (`wp_delete_post_revision`, `wp_delete_post`, `wp_delete_comment`, `delete_option`), pour que hooks et caches suivent. Métadonnées et relations orphelines partent en SQL direct : leur objet parent n'existe plus, il n'y a pas de cache à invalider.
- **Transients expirés : compter ce que le cœur supprime.** `delete_expired_transients( true )` ne supprime que des **paires** valeur + expiration. Un décompte « toutes les expirations passées » laissait un reste après chaque nettoyage (les expirations seules). Ces dernières forment un élément à part, `orphan_transient_timeouts`. L'inverse, un transient sans expiration, n'est **pas** orphelin : c'est un transient sans durée, qui n'expire jamais.
- **Relations de termes.** `term_relationships.object_id` n'est pas toujours un ID d'article (catégories de liens, taxonomies enregistrées sur les utilisateurs). La purge fonctionne donc par **liste blanche** : seules les taxonomies enregistrées et rattachées uniquement à des types de contenu sont concernées. La première version excluait les taxonomies « non contenu » par liste noire. Or celle-ci ne voit que les taxonomies enregistrées au moment du nettoyage : dès qu'une extension de types de membres était désactivée, ses relations vers des utilisateurs passaient pour orphelines et étaient supprimées définitivement (constat de revue, PR #59).
- **Optimisation.** Une table n'est signalée comme fragmentée qu'à partir de 1 Mo d'espace libre, et si cet espace dépasse 20 % de sa taille. Les tables InnoDB sont ignorées quand `innodb_file_per_table` est désactivé. Sans ces seuils, `Data_free` gonflait le total : en tablespace partagé, chaque table rapporte l'espace libre du fichier commun, et InnoDB garde quelques Mo réservés qu'aucun `OPTIMIZE` ne libère. La section ne se vidait donc jamais. Un échec d'`OPTIMIZE TABLE` n'est pas une erreur SQL mais une ligne `Msg_type = error`, que `optimize()` lit explicitement.
- **Tables d'extensions** : tables du préfixe hors `$wpdb->tables( 'all', false )` (et hors `wp_2_…` en multisite). L'extension propriétaire est devinée à partir du premier segment du nom court, comparé au dossier et au nom des extensions installées. Sous 3 caractères (`wc`, `e`), la comparaison se fait uniquement par `OWNER_ALIASES` (filtre `lumia_db_table_owner_aliases`), sinon le jeton correspondrait à tout. Aucune suppression automatique : la suppression réutilise la modale de saisie du nom (`openDropModal( table )`, cible dans `db.dropTarget` et non plus `db.currentTable`) et l'endpoint `lumia_db_drop_table`.
