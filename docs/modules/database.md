# Database module

`includes/Modules/Database/Module.php` + `assets/admin/js/modules/database.js`. Table explorer/editor on top of `$wpdb`. `Module.php` is a thin AJAX layer (no settings: `get_settings()`/`save_settings()`/`get_defaults()` are no-ops); the whole interface is built client-side from a two-pane template (`settings-template.php`: the table list in a sidebar + Data/Structure/SQL query tabs). Required capability: `manage_network_options` on multisite (see [core.md](../core.md#required-capability)).

AJAX actions: `lumia_db_get_tables`, `lumia_db_get_rows`, `lumia_db_get_structure`, `lumia_db_update_row`, `lumia_db_delete_row`, `lumia_db_insert_row`, `lumia_db_truncate`, `lumia_db_drop_table`, `lumia_db_export_sql`, `lumia_db_run_query`, and for the cleanup `lumia_db_cleanup_scan`, `lumia_db_cleanup_run`, `lumia_db_cleanup_optimize`.

## Security model

All server-side, never trust the client.

- **Table/column names**: go through `read_table()` → `validate_table()` (checked against `information_schema.tables` for the current database) and are filtered against `get_columns_map()` (`SHOW COLUMNS`). Uses `sanitize_text_field` (NOT `sanitize_key`) so that mixed-case identifiers survive.
- **Typing**: `column_format()` maps each column to `%d`/`%f`/`%s` for `$wpdb->update`/`insert`/`delete`; NULL is explicit (`set_null` flag / null value), rejected server-side if the column is `NOT NULL`.
- **Free-form SQL editor** (`ajax_run_query`). All the guard-rails test the query **normalized** by `normalize_sql()`, never the raw string; it is the original that is then executed.
  - `normalize_sql()` makes three passes, and **the order is the whole point**: neutralize the literals (`'…'`, `"…"`, `` `…` ``) first, because a comment opener inside a string opens nothing, and treating it as one would truncate the normalized query and hide what follows; then strip the comments (`/* */`, `--`, `#`); then collapse the whitespace. The hole the audit exploited was there: MySQL accepts an empty comment as a word separator, so a `DROP` followed by an empty comment and then `DATABASE` looked like no forbidden keyword while being executed as `DROP DATABASE`. **Extending the blacklist changes nothing here**, as there are infinitely many ways to write a space.
  - `find_forbidden_keyword()` compares **whole words** ("migrant" no longer contains "GRANT"). `FORBIDDEN_KEYWORDS` also covers the MySQL server's disk access: `INTO OUTFILE`, `INTO DUMPFILE`, `LOAD DATA`, `LOAD_FILE`.
  - `is_read_query()` is **not** based on the first word: a `SELECT` can write (`INTO OUTFILE`), a `WITH … DELETE` opens with a read word, and `SELECT 1; DELETE …` hides a second statement. All three are therefore required: a read opening word, no write verb elsewhere, no inner semicolon. The direction of the error is deliberate: classifying a read as a write costs one more confirmation, the opposite costs a table. `CREATE`/`DROP` are deliberately left out of the write-verb list, so that `SHOW CREATE TABLE` stays a read.
  - Any write requires `$_POST['confirm']` (`database.js` pre-confirms via `window.lumiaModal` and **mirrors** `normalize_sql()`/`is_read_query()`; otherwise the interface believes the query harmless and the server answers `needs_confirm`); without it, `needs_confirm` is returned.
  - The `QUERY_ROW_CAP` ceiling (1000) only applies to queries opened by `SELECT` or `WITH`: `SHOW`, `DESCRIBE` and `EXPLAIN` return an already finite set and **do not accept a `LIMIT`**: adding one turned `SHOW CREATE TABLE x` into a syntax error. The presence of a `LIMIT` is read on the normalized form, otherwise a `/* LIMIT 1 */` comment bypassed the cap.
- `friendly_db_error()` translates the common MySQL errors (duplicate entry, FK constraint, NOT NULL, incorrect value) into readable messages.
- **Export** (`ajax_export_sql`): values are emitted according to their type (numerics unquoted, hex `0x…` for binary, `NULL`, explicit column list, `SET NAMES utf8mb4`). Strings go through `$wpdb->remove_placeholder_escape( esc_sql( … ) )`: since WP 4.8.3, `esc_sql()` replaces every `%` with a hash token that only `$wpdb->prepare()` removes. Outside `prepare()`, the token stayed in the dump, and a `50% off` value came back as `50{64 hex characters} off` on re-import (fixed in issue #50).

## Interface

The Data / Structure / SQL query tabs use the shared `lumia-tabs` component (see [design-system.md](../design-system.md#tabs)): `admin.js` handles the display, and `database.js` only loads the open view on the `lumia:tab` event, ignoring it as long as no table is chosen (on load, the remembered tab is restored before any selection). `switchTab()` goes through `window.lumiaTabs.activate()`, which emits the event even if the tab is already open: changing table therefore does reload the data. Each panel keeps `.lumia-db__tab-content`, whose `display:flex` is neutralized by `.lumia-tabs__panel[hidden]`, which is more specific.

The layout height is pure CSS through the `.lumia-admin-main:has(.lumia-db)` flex chain (no JS resize handler). The SQL history is local to the browser (`localStorage`, with a clear button), not persisted server-side. Every visible JS string goes through `lumiaAdmin.i18n` (filled by `get_admin_js_data()`). No editing in the Structure tab, no CSV export.

## Cleanup

Replaces WP-Sweep (issue #16). Logic in `Cleanup.php`, opened by the "Cleanup" entry at the top of the sidebar (global view, outside the selected table). Dedicated, typed endpoints: the item to purge is a key of `Cleanup::items()`, never SQL, and nothing goes through `ajax_run_query`. Scope: the current site (`$wpdb->prefix`).

- **In batches.** `lumia_db_cleanup_run` purges at most `Cleanup::BATCH` (200) objects and returns `deleted` + `remaining`; the JS calls again as long as both are non-zero. A batch with `deleted = 0` stops the item: without that, an object that WordPress refuses to delete looped forever. `OPTIMIZE TABLE` follows the same logic, one call per table, because it rebuilds a whole InnoDB table.
- **WordPress API when the object has one** (`wp_delete_post_revision`, `wp_delete_post`, `wp_delete_comment`, `delete_option`), so that hooks and caches follow. Orphaned metadata and relations are deleted with direct SQL: their parent object no longer exists, there is no cache to invalidate.
- **Expired transients: count what core deletes.** `delete_expired_transients( true )` only deletes **pairs** of value + timeout. A count of "all past expirations" left a remainder after each cleanup (the lone timeouts). Those form a separate item, `orphan_transient_timeouts`. The opposite, a transient without a timeout, is **not** an orphan: it is a transient without a duration, which never expires.
- **Term relationships.** `term_relationships.object_id` is not always a post ID (link categories, taxonomies registered on users). The purge therefore works by **allowlist**: only the registered taxonomies attached solely to post types are concerned. The first version excluded the "non-content" taxonomies with a blocklist. But that list only sees the taxonomies registered at cleanup time: as soon as a member-types plugin was deactivated, its relations to users looked like orphans and were deleted for good (review finding, PR #59).
- **Optimization.** A table is only reported as fragmented from 1 MB of free space, and if that space exceeds 20% of its size. InnoDB tables are ignored when `innodb_file_per_table` is disabled. Without these thresholds, `Data_free` inflated the total: in a shared tablespace, each table reports the free space of the common file, and InnoDB keeps a few reserved MB that no `OPTIMIZE` releases. The section therefore never emptied. A failing `OPTIMIZE TABLE` is not an SQL error but a `Msg_type = error` row, which `optimize()` reads explicitly.
- **Plugin tables**: prefixed tables outside `$wpdb->tables( 'all', false )` (and outside `wp_2_…` on multisite). The owning plugin is guessed from the first segment of the short name, compared with the folder and the name of the installed plugins. Under 3 characters (`wc`, `e`), the comparison is done only through `OWNER_ALIASES` (`lumia_db_table_owner_aliases` filter), otherwise the token would match everything. No automatic deletion: deletion reuses the name-typing modal (`openDropModal( table )`, target in `db.dropTarget` and no longer `db.currentTable`) and the `lumia_db_drop_table` endpoint.
