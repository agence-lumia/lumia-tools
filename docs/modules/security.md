# Security module

`includes/Modules/Security/` — `Module.php`, `ClientIp.php`, `RateLimiter.php`, `LoginUrlHandler.php`, `HardeningService.php`. Settings stored under `lumia_module_security` (`authentication` / `hardening`, posted flat by the form: see `to_form_payload()`).

## ClientIp

Single source of truth for the visitor's IP. Proxy headers (`CF-Connecting-IP`, `X-Forwarded-For`) are sent by the client: they are read **only** if the administrator has declared the topology through the `authentication.ip_source` setting (`remote_addr` by default). Reading them unconditionally made the rate limiter bypassable — a new header per request, a new counter — and let anyone spoof an IP from the whitelist. Never resolve the IP anywhere else: `RateLimiter` and `Module` each had their own version, one taking the first entry of `X-Forwarded-For` and the other the last, so failures were counted under a key the lockout never read. For `x_forwarded_for`, the **last** entry is the one written by the closest proxy — the ones on its left come straight from the incoming request.

## RateLimiter

Hooked on the `authenticate` filter at priority 999 (returns a `WP_Error` to block). Failures are counted through `wp_login_failed`. Reset through `wp_login`. `maybe_block_login($user)` is the filter callback.

**Enabled by default** (`authentication.rate_limiting => true`, #77). It used to be disabled: an audit of the production sites (09/10/2026) found it active on 2 sites out of 8, although the module was active everywhere — on 5 sites, `lumia_module_security` did not even exist in the database. `wp-login.php`, the WooCommerce login (`/mon-compte/`, which goes through `wp_signon()` and therefore `authenticate`), XML-RPC and application passwords could be guessed with no limit. Since `merge_defaults()` is recursive, the new value applies by itself to sites with no option or without this key; a `false` explicitly saved is still respected.

**Application passwords.** They do NOT go through `wp_authenticate()`: `wp_validate_application_password()` calls `wp_authenticate_application_password()` directly, so neither the `authenticate` filter nor the `wp_login_failed` action is consulted — application passwords could be guessed with no limit at all, even from an IP already blocked on the form. The core offers no refusal filter on this path: the only stopping point **before** the password comparison is `application_password_is_api_request`, to which we answer `false` when `RateLimiter::is_locked()` (the function then returns before any check, and the request goes out anonymous, hence a 401). Counting goes through the `application_password_failed_authentication` action. `is_locked()` exists precisely for the authentication paths that have no `WP_Error` to return.

## LoginUrlHandler

Hooked on `wp_loaded` to intercept both the custom login slug and direct access to `wp-login.php`. Must check `action !== 'logout'` before redirecting logged-in users. Two easy-to-miss path rules: compare `basename($path)` to detect `wp-login.php` (testing the whole URI made every `?redirect_to=…wp-login.php` answer 404 — which WordPress generates itself), and anchor the custom slug on the **installation path** taken from `site_url()`, not on `/` (a subdirectory install serves `/wp/connexion`, and a pattern anchored on `/connexion` matches nothing while `wp-login.php` stays blocked — complete lockout). Build the login URL from `get_option('siteurl')`, never from `site_url()`: this class filters `site_url`, calling it here recurses.

**Escape hatch**: `define( 'LUMIA_DISABLE_LOGIN_URL', true )` in `wp-config.php` restores `wp-login.php`. Without it, a forgotten slug has no recovery path from the browser.

**`wp-login.php` is not only a login form.** `action=postpass` (password-protected content) and `action=confirmaction` (GDPR requests) must keep being served at their original address: `LoginUrlHandler::PASSTHROUGH_ACTIONS` lets them through **before** the block. Without it, the form of a protected post answered 404 (it posts to `wp-login.php?action=postpass`, which `filter_site_url()` deliberately leaves intact).

**Validated login slug.** `Module::sanitize_login_slug()`: `sanitize_title()` per segment, refusal of any first segment starting with `wp-` and of the reserved ones (`admin`, `login`, `index`, `feed`, `xmlrpc`…). `admin` and `login` are redirected by the core to wp-admin/wp-login (`wp_redirect_admin_locations`): such a slug locks the administrator out of the site. A refused slug leaves the previous value in place.

## HardeningService — account enumeration

Five surfaces, one promise; forgetting one amounts to blocking nothing.

- **Author archives**: the block lives on `parse_request` **@1**, not on `template_redirect`. Hooked there, it ran after `redirect_canonical`: WordPress answered `301 Location: /author/lumia/` — the identifier leaked in the header, before the block could act, and only the final archive page was protected. **Both** variables are handled (`author` for `?author=N`, `author_name` for `/author/slug/`), then a 404 is forced on `wp` (removing the variable is not enough: the request would fall back to the post list). The answer is a **uniform 404**, never a 403: the three distinct codes of before (301 / 403 / 404) were an oracle on their own — one could tell an account existed without even reading the page.
- **REST**: `prevent_rest_user_enumeration()` lets `/wp/v2/users/me` through for any **logged-in** user. Requiring `list_users` (an administrator capability) on the whole `/wp/v2/users` branch returned a 403 to every author or contributor and **broke the block editor**, although this route only discloses the caller's own account. The route test is anchored (`^/wp/v2/users(/|$)`): `strpos()` matched the substring anywhere.
- **oEmbed**: `/wp-json/oembed/1.0/embed` serves `author_name` and `author_url` without authentication, for any post. Both keys are emptied through `oembed_response_data` rather than closing the route — the preview stays functional.
- **Sitemap**: `/wp-sitemap-users-1.xml` lists the author archives and gets indexed. The `users` provider is removed through `wp_sitemaps_add_provider`.
- **Login form**: it set "this identifier is not registered" against "this password does not match identifier X". We go through the **`wp_login_errors`** filter (which receives the `WP_Error` object), and **above all not** through `login_errors` by reading the global `$errors`: `LoginUrlHandler::wp_loaded()` loads wp-login.php with a `require_once` **from a method**, so the `$errors` of wp-login.php is a local variable of that method and never reaches the global scope — the filter would see nothing. The message is replaced while **keeping the code** (wp-login.php uses `incorrect_password` right after to refill the identifier field); `empty_password` and cookie errors stay intact, they say nothing about an account.
- **Lost password**: rewriting the message is not enough, the oracle is in the **shape** of the response — a known account redirects to `?checkemail=confirm`, an unknown account redisplays the form. `mask_lost_password_oracle()` (action `lost_password`) therefore replays the redirect when `invalidcombo` is the only error. The `lostpassword_errors` filter is not suitable: the core adds `invalidcombo` **after** applying it. Accepted caveat: `retrieve_password_email_failure` remains distinguishable — masking it would deprive the administrator of the only signal warning them that their site's e-mail sending is broken, and on a site whose sending works that code never appears.

## `X-Powered-By`

It comes from **PHP** (`expose_php`), not from WordPress: `unset( $headers['X-Powered-By'] )` on the `wp_headers` filter only acted on the array WordPress was about to emit, and the header went out on every response with the setting enabled. `header_remove()` is needed, hooked as early as possible (`init` @0 and `send_headers` @0) since it only acts while the headers have not been sent. The real solution remains `expose_php = Off`: it also covers what does not go through WordPress.
