# Files module

`includes/Modules/Files/` — `FileManager.php` is a standalone file-system service rooted at `ABSPATH`; `Module.php` is a thin AJAX/admin-post layer (`ajax_list`, `ajax_delete`, `ajax_rename`, `ajax_move`, `ajax_mkdir`, `ajax_zip`, `ajax_extract`, `ajax_get_content`, `ajax_save_content`, `ajax_upload`, plus a streamed download handler `admin_post_lumia_files_download`). Required capability: `manage_network_options` on multisite (see [core.md](../core.md#required-capability)).

Every path input goes through `get_post_path()` (`sanitize_text_field` + `rawurldecode`) before reaching `FileManager` — never trust a client-supplied path. `FileManager::save_content()` throws on a read-only or non-writable target: never swallow that return value, otherwise the editor announces a successful save although nothing reached the disk.

`FileManager` calls PHP directly (`unlink`, `rename`, `rmdir`, `file_put_contents`, `is_writable`) rather than `WP_Filesystem`: the latter may go through FTP/SSH under a different user than PHP, and the permissions shown in the list would no longer match what the operations can actually do. The PHPCS rule `WordPress.WP.AlternativeFunctions` is therefore disabled for the whole file.

## Code editor

The editor is CodeMirror **shipped with WordPress** (`wp-codemirror`), not a bundled copy. `Module::enqueue_code_editor()` runs on `admin_enqueue_scripts` at **priority 5** (Admin reads `get_admin_js_data()` at 10) and calls `wp_enqueue_code_editor()` once per entry of `EDITABLE_EXTENSIONS`, collecting the per-extension settings in the `codeEditor` JS payload. The core's `wp-admin/js/code-editor.js` already wires up as-you-type autocompletion for HTML/CSS/JS/PHP — do not reimplement it. `wp_enqueue_code_editor()` returns `false` when the user turned syntax highlighting off in their profile; the payload is then emptied and `files.js` falls back to the bare textarea. Keep `EDITABLE_EXTENSIONS` in sync with `isEditable()` in `files.js`.

Only the default (light) CodeMirror theme ships with the core: the dark palette lives in `files.css` under `.lumia-files-editor`. The autocompletion menu is appended to `<body>`: it needs `ul.CodeMirror-hints` (element + class) to win over `ul.CodeMirror-hints { z-index: 101 }` from `wp-admin/css/widgets.css`.

## `DISALLOW_FILE_EDIT` / `DISALLOW_FILE_MODS`

`check_file_mods( bool $editing )` gates every mutating endpoint. These constants are not a cosmetic setting: they say "nobody modifies a file from the browser on this site", and a file manager that ignores them is more permissive than the core editor they disable. They do not cover the same thing — `DISALLOW_FILE_EDIT` means **code editing** (`ajax_save_content`, `ajax_upload`), `DISALLOW_FILE_MODS` any file modification (the previous ones plus rename, move, delete, `mkdir`, zip, extract). **Reading** (listing, preview, download) stays open in both cases: neither says anything about reading.

## Danger mode (`DangerMode`, issue #7)

On sites deployed with the Dokploy WordPress template, `DISALLOW_FILE_EDIT` is injected through `WORDPRESS_CONFIG_EXTRA` (`wp-dokploy-template/docker-compose.yml`): it is not in `wp-config.php`, so the editor looked broken for no visible reason, and nothing in the admin could lift it. The danger mode lifts it **for the Files module only, for one hour** (`DangerMode::TTL`), then falls back to the safe mode by itself.

- **Scope**: only `DISALLOW_FILE_EDIT` (save + upload). `DISALLOW_FILE_MODS` and the `file_mod_allowed` filter always win, and the core theme and plugin editors stay disabled. `check_file_mods()` returns `true` when a write goes through only thanks to the danger mode, which then fires `lumia_files_danger_mode_write` (path, `save` / `upload`).
- **State server side only**: option `lumia_files_danger_mode` (`expires`, `user_id`, not autoloaded). Site-wide, not per user: the constant it lifts is site-wide too. The browser only receives the **remaining seconds** (`DangerMode::to_js()`) and rebuilds its deadline from them, so a wrong client clock does not matter; the server stays the only authority.
- **Expiry enforced twice**: every read compares the deadline to the clock (`state()`), and a single cron event (`lumia_files_danger_mode_expire`) clears the state when nobody comes back to the screen. Both paths go through `clear()`, which reports only if `delete_option()` returned `true`: when the cron and a page load expire it at the same moment, a single "locked" row is written.
- **Expiry has no author**: during a logged-in request, the Activity Log would otherwise credit the visitor who happened to load a page with "locked by hand". The recorder receives `new \WP_User( 0 )` (see [activity-log.md](activity-log.md)); who turned the mode on goes into the `enabled_by` detail.
- **Opt-out**: `add_filter( 'lumia_files_danger_mode_allowed', '__return_false' )` removes the button and stops an active danger mode at once (it is checked on every write).
- **Unlocking again after a missed deadline**: on the Dokploy template WP-Cron is disabled and a system cron runs every few minutes, so the hour can end before the event fires. `enable()` reads `state()` first, which reports the expiry; overwriting the row directly left two "unlocked" rows with no "locked" between them. `clear( 'expired' )` also re-reads the deadline, so an expiry racing a restart does not delete the new hour.
- **Deactivating the module** (`on_deactivate()`), **the plugin** (`Deactivator`, whose cron cleanup removes the expiry event) and **Settings → Reset** (which deletes the module options) all lock it through `disable()` first: the lock is logged while the Activity Log is still loaded, instead of being reported as an expiry days later. Uninstall deletes the option and the cron event.
- **Hooks**: `lumia_files_danger_mode_allowed` and the three `lumia_files_danger_mode_*` actions are plain `apply_filters()` / `do_action()`, not `Compat`: they never existed under an `skmt_` name (same as the `lumia_image_optimizer_*` actions).
- **UI**: a `lumia-notice` above the toolbar (warning when locked, error when active, with the remaining minutes), a toast 5 minutes before the end, and the same state in the **editor header**: the editor covers the screen, and an expiry in the middle of an edit must not force closing it (losing the changes) to unlock again. While writing is refused, the upload input and the editor's Save button are disabled; the refused responses carry the fresh state (`danger`), as does every listing, so a lock from another tab shows up on the next action.

## Translatable strings

The JS strings (toasts, modals, row-action tooltips, confirmation texts) are never literals in `files.js`: `Module::get_admin_js_data()` hands them over under the `i18n` key and `files.js` reads them through its `t( key )` helper. A string with a placeholder (`compressing`, `zipDownloaded`, `compressError`, `selectedCount`, `dangerRemaining`, `dangerBadge`, `dangerSoon`) carries a single `%s` / `%d`, substituted by `fmt()`. The error fallback reuses the generic `error` key of `lumiaAdmin.i18n`, and the cancel button the generic `cancel` key. The editor's "unsaved changes" modal has its own `editorUnsaved*` keys: the core keys of the same meaning (`unsavedTitle`, …) have a different French wording and belong to the core screens. The messages thrown by `FileManager` that used to be hard-coded French (read-only file, write failure, rejected archive, `ZipArchive` missing…) go through `__()` and `sprintf()` like the rest, and so do the ones that were already English (`Not a directory.`, `Invalid path.`…): a message thrown by `FileManager` can reach the user through `wp_send_json_error()` and a toast. The only exception is the constructor's `Root path does not exist`, thrown outside any `try`/`catch` for a missing `ABSPATH`: a fatal configuration error for the developer, never a toast. A caught message is not always shown either: in the batch endpoints (`ajax_delete`, `ajax_upload`), the per-item errors are returned only when every item failed; as soon as one item succeeds, the response is a success and the errors of the others are dropped. The per-file upload errors use the shared `%1$s: %2$s` format, so the French colon gets its space. A file PHP rejected for its size (`UPLOAD_ERR_INI_SIZE`, `UPLOAD_ERR_FORM_SIZE`) gets a dedicated message giving the server limit (`size_format( wp_max_upload_size() )`); every other `UPLOAD_ERR_*` code stays the generic "Upload failed.".
