# Files module

`includes/Modules/Files/` — `FileManager.php` is a standalone file-system service rooted at `ABSPATH`; `Module.php` is a thin AJAX/admin-post layer (`ajax_list`, `ajax_delete`, `ajax_rename`, `ajax_move`, `ajax_mkdir`, `ajax_zip`, `ajax_extract`, `ajax_get_content`, `ajax_save_content`, `ajax_upload`, plus a streamed download handler `admin_post_lumia_files_download`). Required capability: `manage_network_options` on multisite (see [core.md](../core.md#required-capability)).

Every path input goes through `get_post_path()` (`sanitize_text_field` + `rawurldecode`) before reaching `FileManager` — never trust a client-supplied path. `FileManager::save_content()` throws on a read-only or non-writable target: never swallow that return value, otherwise the editor announces a successful save although nothing reached the disk.

`FileManager` calls PHP directly (`unlink`, `rename`, `rmdir`, `file_put_contents`, `is_writable`) rather than `WP_Filesystem`: the latter may go through FTP/SSH under a different user than PHP, and the permissions shown in the list would no longer match what the operations can actually do. The PHPCS rule `WordPress.WP.AlternativeFunctions` is therefore disabled for the whole file.

## Code editor

The editor is CodeMirror **shipped with WordPress** (`wp-codemirror`), not a bundled copy. `Module::enqueue_code_editor()` runs on `admin_enqueue_scripts` at **priority 5** (Admin reads `get_admin_js_data()` at 10) and calls `wp_enqueue_code_editor()` once per entry of `EDITABLE_EXTENSIONS`, collecting the per-extension settings in the `codeEditor` JS payload. The core's `wp-admin/js/code-editor.js` already wires up as-you-type autocompletion for HTML/CSS/JS/PHP — do not reimplement it. `wp_enqueue_code_editor()` returns `false` when the user turned syntax highlighting off in their profile; the payload is then emptied and `files.js` falls back to the bare textarea. Keep `EDITABLE_EXTENSIONS` in sync with `isEditable()` in `files.js`.

Only the default (light) CodeMirror theme ships with the core: the dark palette lives in `files.css` under `.lumia-files-editor`. The autocompletion menu is appended to `<body>`: it needs `ul.CodeMirror-hints` (element + class) to win over `ul.CodeMirror-hints { z-index: 101 }` from `wp-admin/css/widgets.css`.

## `DISALLOW_FILE_EDIT` / `DISALLOW_FILE_MODS`

`check_file_mods( bool $editing )` gates every mutating endpoint. These constants are not a cosmetic setting: they say "nobody modifies a file from the browser on this site", and a file manager that ignores them is more permissive than the core editor they disable. They do not cover the same thing — `DISALLOW_FILE_EDIT` means **code editing** (`ajax_save_content`, `ajax_upload`), `DISALLOW_FILE_MODS` any file modification (the previous ones plus rename, move, delete, `mkdir`, zip, extract). **Reading** (listing, preview, download) stays open in both cases: neither says anything about reading.

## Translatable strings

The JS strings (toasts, modals, row-action tooltips, confirmation texts) are never literals in `files.js`: `Module::get_admin_js_data()` hands them over under the `i18n` key and `files.js` reads them through its `t( key )` helper. A string with a placeholder (`compressing`, `zipDownloaded`, `compressError`, `selectedCount`) carries a single `%s` / `%d`, substituted by `fmt()`. The error fallback reuses the generic `error` key of `lumiaAdmin.i18n`, and the cancel button the generic `cancel` key. The editor's "unsaved changes" modal has its own `editorUnsaved*` keys: the core keys of the same meaning (`unsavedTitle`, …) have a different French wording and belong to the core screens. The messages thrown by `FileManager` that used to be hard-coded French (read-only file, write failure, rejected archive, `ZipArchive` missing…) go through `__()` and `sprintf()` like the rest, and so do the ones that were already English (`Not a directory.`, `Invalid path.`…): every message thrown by `FileManager` reaches the user through `wp_send_json_error()` and a toast. The only exception is the constructor's `Root path does not exist`, thrown outside any `try`/`catch` for a missing `ABSPATH`: a fatal configuration error for the developer, never a toast. The per-file upload errors use the shared `%1$s: %2$s` format, so the French colon gets its space.
